第 1 章

依赖注入到底解决什么

一切都从一个朴素的问题开始：Emailer 需要一个 SpellChecker，这个 SpellChecker 从哪来？本章走完四种答案——自己 new、手工传入、工厂、服务定位器——看着它们一个个撞墙，最后才轮到注入器出场。

  • 对象图 Object graph
  • Construction by hand
  • Factory / Service Locator
  • 好莱坞原则
  • viral injection

1.1把对象看成服务

程序是对现实流程的自动化：发一封邮件、处理一张订单。参与流程的角色被建模成对象，对象之间靠方法调用协作。当一个对象要完成工作必须借助另一个对象时，前者叫客户（client / dependent），后者叫服务（service / dependency）。

把这些引用关系画出来，就是对象图（object graph）。DI 这门学问的全部内容，用一句话概括就是：

全书的定义

DI 关心的是如何可靠、高效地构建对象图，以及围绕它的策略、模式与最佳实践。

注意这里说的是"构建"，不是"使用"。使用对象图的代码（业务逻辑）在有没有 DI 的情况下写法完全一样——这是 DI 号称"非侵入"的根据。变的只是谁来负责 new。

1.2四种答案，三堵墙

答案零：自己 new（不是答案）

public class Emailer {
    private final SpellChecker spellChecker;

    public Emailer() {
        this.spellChecker = new EnglishSpellChecker();   // 把创建封装进来了
    }

    public void send(String text) { spellChecker.check(text); ... }
}

这段代码有两个致命问题，而且它们是同一个问题的两面：

  • 不可测。想验证 send() 有没有真的调用拼写检查？你没有任何缝隙把 mock 塞进去。
  • 不可变体。想要一个法语版的 Emailer？做不到。Emailer 把"我用哪种拼写检查"这个决定据为己有了。

用书里的话说：它封装的不只是依赖，还封装了依赖的创建。这两者必须分开。

答案一：手工构造（construction by hand）

不封装创建，让外部传进来。用 setter 或者构造器都行：

setter 传入
Emailer e = new Emailer();
e.setSpellChecker(new FrenchSpellChecker());
// 可能忘记调用 setter → NPE
构造器传入
Emailer e = new Emailer(new FrenchSpellChecker());
// 契约显式：不可能"忘记"

测试立刻变得可行了。但这只是把负担转嫁给了调用方，并没有消灭它：

  • 同一个对象在十处使用，接线代码就要重复十遍；
  • 改动对象图的任何一层，所有调用方都可能要跟着改；
  • 更严重的是破坏封装：客户被迫知道服务的内部构造。

答案二：工厂模式

把接线搬进第三方对象：

public class EmailerFactory {
    public Emailer newJapaneseEmailer() {
        Emailer service = new Emailer();
        service.setSpellChecker(new JapaneseSpellChecker());
        service.setAddressBook(new EmailBook());
        service.setTextEditor(new SimpleJapaneseTextEditor());
        return service;
    }
}

客户端代码干净了：new EmailerFactory().newJapaneseEmailer()。但三堵墙开始出现。

墙一：工厂爆炸。每一个服务要一个工厂，每一个变体还要一个方法。把 EmailBook 换成 PhoneAndEmailBook，你要在三个方法里做三处一模一样的修改。顺着这条路走到极端，你会写出这种东西：

Emailer service = new EmailerFactoryFactory()
        .newAdvancedEmailerFactory()
        .newJapaneseEmailerWithPhoneAndEmail();

墙二：测试工厂的客户。要测试 EmailClient（它从工厂取 Emailer），你得让工厂返回 mock。于是工厂被迫长出一个静态 set()：

@Test void testEmailClient() {
    MockEmailer mock = new MockEmailer();
    EmailerFactory.set(mock);              // 静态共享状态
    try {
        new EmailClient().run();
        assert mock.correctlySent();
    } finally {
        EmailerFactory.set(null);          // 忘了清理就污染后续测试
    }
}

墙三：并行测试直接崩。那个静态字段是全局的。多个测试线程并发跑，互相踩踏，测试结果完全不可信。这是共享状态的本质问题，第 5 章会正面处理它。

答案三：服务定位器

服务定位器是"能生产任何服务的工厂"，靠键来区分：

Emailer emailer = (Emailer) new ServiceLocator()
        .get("JapaneseEmailerWithPhoneAndEmail");

它解决了工厂爆炸——一个定位器顶所有工厂。JNDI 就是这个模式的经典实现。但它没解决另外两堵墙，还添了新的：

  • 本质仍是工厂 → 测试与共享状态问题原封不动；
  • 键是不透明的字符串，绑错类型要到运行时才炸；
  • 把服务信息编码进标识符（"JapaneseEmailerWithPhoneAndEmail"）冗长且依赖约定；
  • 最要命的：客户端代码必须显式去"要"。这行 locator.get(...) 就写在业务方法里，它是业务逻辑的一部分，测试时躲不开。

1.3好莱坞原则

"Don't call us; we'll call you."（别打给我们，我们会打给你。）经纪人这么对演员说，注入器这么对你的类说。

关键差别只有一个：构造、组装、接线的工作，交给一个外部框架完成。你的类只是声明"我需要什么"，然后闭眼等着东西送上门。

// 客户和服务，都不知道对方是怎么被造出来的
public class SimpleEmailClient {
    private final Emailer emailer;

    @Inject
    public SimpleEmailClient(Emailer emailer) {   // 只是声明需求
        this.emailer = emailer;
    }

    public void sendEmail() { emailer.send(readMessage()); }
}

IoC 和 DI 是一回事吗

不完全是。IoC（控制反转）泛指一切"责任反转"：Java EE 容器里的模块、框架自动调用的测试方法、鼠标点击触发的事件处理器……都算。DI 只是 IoC 的一个实例。作者干脆在书里弃用了 IoC 这个词（以及"IoC 容器"这个"邪恶的表亲"），只用三个精确术语：

术语含义
好莱坞原则依赖是"被送到"客户手上的，而不是客户去要的
依赖注入器实现这一原则的框架/库
依赖注入基于这一原则设计应用时的全部考量

题外话：dependency injection 这个词的流行始于 Martin Fowler 2004 年那篇 Inversion of Control Containers and the Dependency Injection Pattern，是他与 PicoContainer 作者、Rod Johnson 等人讨论后的产物。

1.4注入器 ≠ 服务定位器（虽然长得像）

第 2 章你会看到 injector.getInstance(Emailer.class)，跟 locator.get("Emailer") 简直一模一样。作者自己也承认：注入器确实可以当服务定位器用。区别在三点，而这三点就是全部价值所在：

  • 调用者不同。调用注入器的是应用启动器，不是业务代码。启动器不参与程序行为，所以它不进入测试范围。
  • 只取根对象。整个应用通常只 getInstance() 一次，其余全靠级联。在 Web 应用里，这一次调用还被集成层（guice-servlet、Spring 的 DispatcherServlet）替你做掉了。
  • 作用域。注入器返回的实例取决于当前执行上下文——同一个键，在这个请求里和那个请求里可以是不同实例。这一点服务定位器完全没有，也是第 5、6 两章的全部主题。
⚠ 陷阱

把注入器注入到业务类里，然后在方法里调 injector.getInstance(...)——这就是把 DI 退化回服务定位器，同时还多背了一个框架依赖。这是新手最常犯的错。业务类里出现 Injector / ApplicationContext 类型的字段，基本都是设计信号。

  • 手工构造平反了。原书把它当成"过渡方案"，今天它在单元测试里是首选——测试里就该 new Emailer(mockChecker)，不要启动容器。第 4 章会重申这点。近年 .NET 圈流行的 Pure DI（完全不用容器，在 Composition Root 里手写接线）更是把它抬成了正经架构选项。

第 1 章说清了"为什么"，这一章处理"怎么做"。三步：启动注入器 → 取出根对象 → 用它。真正有深度的是第三个问题——注入器凭什么认出你要的那个实现？答案是键（key），而键的设计直接决定了错误在编译期暴露还是在生产环境暴露。

2.1注入器自己也是个服务

注入器要先被构造出来才能用。这一步叫 bootstrap，发生的时机取决于应用类型：

时机典型场景今天的等价物
Web 应用部署时的 init 阶段Servlet 容器加载 warSpring Boot 的 SpringApplication.run()
桌面程序启动时Swing/JavaFX 的 main同上，或手写 Composition Root
按需，每次用到就建一个远程调用几乎绝迹（太贵）
懒加载，首次使用时调试/测试Guice 的 Stage.DEVELOPMENT

绝大多数情况下，注入器的启动就等于应用的启动。这不是巧合——注入器持有整个对象图，它的生命周期天然等于应用的生命周期（第 7 章会展开）。

2.2三行代码，三件事

Guice.createInjector().getInstance(Emailer.class).send("Hello");
//     ①创建注入器            ②取根对象            ③用它

拆开写就是：

Injector injector = Guice.createInjector();
Emailer emailer = injector.getInstance(Emailer.class);
emailer.send("Hello!");

Spring 的等价物：

BeanFactory injector = new FileSystemXmlApplicationContext("email.xml");
Emailer emailer = (Emailer) injector.getBean("emailer");   // 注意这个强制转型
emailer.send("Hello!");

PicoContainer：

MutablePicoContainer injector = new DefaultPicoContainer();
injector.addComponent(Emailer.class);
injector.addComponent(SpellChecker.class);
injector.getComponent(Emailer.class).send("Hello!");

请注意第三行在三个库里完全一样：emailer.send("Hello!")。这就是"DI 不是侵入式技术"的具体含义——业务代码不因为换了容器而改变。

⚠ 注意 Spring 那行强制转型

getBean("emailer") 返回 Object，你必须转型。这个转型是运行时检查的。配置里绑错了类型，编译器一声不吭，程序跑到这一行才 ClassCastException。这正是 2.4 节要解决的问题。

今天的写法：context.getBean(Emailer.class)，泛型返回，转型消失。但更好的写法是——根本不调 getBean。

2.3告诉注入器怎么装配：五种方式

Spring 的 XML（2009 主流，今天的历史文物）

<beans ...>
    <bean id="emailer" class="Emailer">
        <constructor-arg ref="spellChecker"/>
    </bean>
    <bean id="spellChecker" class="SpellChecker"/>
</beans>

更紧凑、也更好的写法是内联嵌套：

<bean id="emailer" class="Emailer">
    <constructor-arg><bean class="SpellChecker"/></constructor-arg>
</bean>

好处有两个，而且第二个很重要：SpellChecker 的描述就在 Emailer 内部；并且它没有自己的标识符，所以只能在 Emailer 的语境里被取到。这叫依赖封装——你不会不小心把给邮件用的拼写检查器接到别的对象上去。

Guice 的 Module

public class EmailerModule extends AbstractModule {
    @Override protected void configure() {
        bind(Emailer.class);
        bind(SpellChecker.class);
    }
}

和 XML 的 <bean> 语义完全对应，但它是 Java 代码，编译器会检查。

PicoContainer 的贪婪构造器

injector.addComponent(Emailer.class);
injector.addComponent(SpellChecker.class);
injector.addComponent(TextEditor.class);

Pico 默认贪婪地挑参数最多的构造器。Emailer 如果有 (SpellChecker) 和 (SpellChecker, TextEditor) 两个构造器，它会选后者。作者评价："这个默认行为令人困惑"。今天 Spring 的规则更温和也更明确：只有一个构造器时自动用它；多个时必须用 @Autowired 指定。

Spring 的 autowiring

<bean id="spellChecker" class="SpellChecker"/>
<bean id="emailer" class="Emailer" autowire="constructor"/>

Spring 2.5 起可以直接在构造器上打 @Autowired 来消除歧义，autowire 属性就不需要了。这一步是 Spring 从 XML 走向注解的转折点，而这本书恰好写在转折点上。

2.4键：这一章真正的重点

同一个 Emailer 类，配上英语/法语/日语拼写检查器，是三个不同的变体（variant）。它们都实现同一份契约，所以注入器需要某种标签来区分它们。这个标签就是键。

好的键有三个性质：

  • 唯一（unique）—— 一个键只对应一个对象图；
  • 任意（arbitrary）—— 能描述用户自造的任何变体，不能只有服务名；
  • 显式（explicit）—— 清楚说明这个实现干什么。

字符串键的死穴

书里举了一个绝妙的例子。任天堂 Wii 和游戏《半条命》：

<bean id="nintendo.wii" class="com.nintendo.Wii">
    <constructor-arg ref="game.HalfLife"/>

}

键起得完美——唯一、任意、显式，还用了命名空间。但程序会在运行时抛 UnsatisfiedDependencyException。在配置文件里，你无从得知一个字符串键绑的是什么类型。

更糟的是拼错左边的情况（第 10 章会重提）：拼错一个属性名，配置系统往往一声不吭地用默认值继续跑，连集成测试都发现不了。

方案 B：类型键

bind(WiiGame.class).to(HalfLife.class);   // ← 这行编译不过

编译器报错："没有接受 HalfLife 参数的 to() 方法"。错误在你敲键盘的那一刻就被 IDE 标红了。

方案 C：组合键（正解）

把两者拼起来。第一部分是类型（安全地指出契约），第二部分区分变体：

[Emailer.class, "english"]        // 类型 + 字符串：还是会拼错
[Emailer.class, English.class]    // 类型 + 注解类型：拼错 = 编译错误 ✓

bind(SpellChecker.class).annotatedWith(French.class).to(FrenchSpellChecker.class);

@Inject

"客户写了 @English，它不就和英语实现耦合了吗？"——没有。你可以把 @English 绑到 FrenchSpellChecker 上，客户端一行都不用改，也感知不到。@English 是一个抽象标签，不是实现名。这一点和"接口名不该叫 IArrayListUserDao"是同一个道理。

本章的落点。渲染网页、发邮件、买股票、检查拼写——这些是应用逻辑。构造对象图、拿数据库连接、开 socket——这些是基础设施逻辑。DI 的价值就是把后者从前者里剥出去，剥干净。

① XML 配置：已经出局

Spring 官方文档从 5.x 起就以 Java 配置为主，Spring Boot 从来就不推荐 XML。今天等价的三层写法：

// 1. 组件扫描 —— 相当于原书的"类结构推断"，负责 90% 的接线
@Service
class Emailer {
    private final SpellChecker checker;
    Emailer(SpellChecker checker) { this.checker = checker; }   // 唯一构造器，@Autowired 可省

// 2. @Configuration —— 相当于原书的"XML / DSL"，处理推断不了的部分
@Configuration
class MailConfig {
    @Bean SpellChecker english() { return new EnglishSpellChecker(); }

// 3. Spring 7 新增 BeanRegistrar —— 程序化注册，且对 AOT/原生镜像友好
class MailRegistrar implements BeanRegistrar {
    public void register(BeanRegistry r, Environment env) {
        r.registerBean(SpellChecker.class, spec -> spec.supplier(ctx -> new EnglishSpellChecker()));
    }
}

Spring 的 bean 名今天多半是自动生成的类名首字母小写，人工起名的场合少了。但"用命名空间组织服务"这条建议转移到了包结构上：com.acme.order.domain / …order.infra.jpa / …order.web。原书 dao. / biz. / util. 那套前缀，今天是分层包名和 Spring Modulith 之类的模块化约束。

  • Guice 7.0（2023-05）：仅支持 jakarta.inject；guice-servlet/guice-persist 也改成 jakarta.servlet/jakarta.persistence。6.0 是双命名空间的过渡版。

  • PicoContainer：停更。它的"贪婪构造器"设计被历史否定，取而代之的是 Spring 的"唯一构造器自动注入"规则。
  • 新流派：Dagger 2（2.60.x）、Micronaut、Quarkus 在编译期生成接线代码。它们把本章的"键"检查从运行时彻底移到了 javac 的注解处理器里——某种意义上是把作者的选型标准做到了极致。

第 3 章

注入方式的取舍

构造器注入还是 setter 注入？作者反复强调：这不是口味问题。选错会导致对象半成品、线程可见性丢失、以及一类无解的初始化死锁。本章给出完整的决策依据，以及当依赖"来得太晚"或"用一次就没了"时的三种补救模式。

  • 构造器 / setter / 接口注入 / 方法装饰
  • 不可变与对象有效性
  • 构造器金字塔
  • 循环引用 · in-construction
  • Provider / Assisted / Builder
  • 密封代码

3.1四种注入习语

差别的根源在于构造器和普通方法的语言级差异。构造器：不返回值、必须执行完对象才算构造好、能给 final 字段赋值、每个实例只调一次、不能有任意名字、不能是虚方法。这些限制既是它的短板，也是它的全部优势来源。

构造器注入
public class Emailer {
    private final SpellChecker checker;   // final ✓

    public Emailer(SpellChecker checker) {
        this.checker = checker;
    }
}
setter 注入
public class Emailer {
    private SpellChecker checker;         // 不能 final

    public void setSpellChecker(SpellChecker c) {
        this.checker = c;
    }
}

接口注入（已淘汰，但思想还在）

每个依赖一个角色接口：

public class Starship implements PhaserMountable, ReactorMountable, ShuttleDockable {
    public void mount(Phaser phaser)  { this.phaser = phaser; }
    public void mount(Reactor r)      { this.reactor = r; }
    public void dock(Shuttle s)       { this.shuttle = s; }
}

优点是方法名可以起得有意义（load(Cargo) 比 setCargo(Cargo) 好读）。缺点致命：极度啰嗦，每个依赖一个接口，类签名被淹没。只有已消亡的 Apache Avalon 支持它。

但这个思路没死：它演化成了角色接口 / 生命周期回调接口——Spring 的 InitializingBean、BeanFactoryAware，第 7 章的 Suspendable/Resumable，都是这个模式的后代。

方法装饰（AOP 注入）

让一个方法本身变成注入器背后的工厂。Pez 糖果机：

public class Dispenser {
    public Pez dispense() { return null; }    // 空实现，永远不会被真的调用
}
<bean id="dispenser" class="candy.Dispenser">
    <lookup-method name="dispense" bean="pez"/>
</bean>

Spring 拦截 dispense()，每次调用返回一个新的、由容器完整装配的 Pez。用途稀少但确实存在——它解决的是 3.3 节的"重注入问题"。这个特性今天还在，叫 lookup method injection，但 ObjectProvider 已经是更好的写法。

⚠ 字段注入

Guice 和 Spring 都支持直接往字段上注入：

public class BrewingVat {
    @Inject Barley barley;
    @Inject Yeast yeast;
}

作者的评价一针见血："写教程和示例代码时很好用，实践中价值很小。"因为——① 测试里没法设置依赖（无论真的还是 mock），单元测试直接失效；② 字段是构造后才赋值的，不可能声明为 final。

2026 补充：这个判断已经成为行业共识。Spring 官方文档明确不推荐字段注入，IntelliJ IDEA 会对 @Autowired 字段直接报 warning（"Field injection is not recommended"）。Dagger 保留了字段注入，但只用于 Android 那些"实例由系统创建、你插不了手"的场景（Activity、Fragment）——这恰好是 3.4 节"密封代码"的现代版本。

3.2构造器 vs setter：五轮交锋

第 1 轮：不可变性 —— 构造器胜

只有构造器能给 final 字段赋值。final 不只是"防止手滑改掉"，它还是 Java 内存模型的安全发布保证：构造器正常返回后，所有线程都能看到 final 字段的正确值，不需要额外同步。这一点第 9 章会详细展开，它是本书最重要的技术结论之一。

第 2 轮：对象有效性 —— 构造器胜

作者称之为"最被低估的 OOP 设计问题"。看这个 Blender：

public class Blender {
    private GlassJar jar;
    private Blades blades;

    @Inject
    public void setJar(GlassJar jar) { this.jar = jar; }

    public void setBlades(Blades blades) { this.blades = blades; }   // 少了 @Inject

    public void frappe() {
        jar.fillWithOranges();
        blades.run();     // NullPointerException
    }
}

编译通过，容器启动正常，一切看起来都对——直到 frappe() 被调用。而且单元测试里也会踩到同样的坑：

@Test void blendOranges() {
    new Blender().frappe();   // 忘了调 setter → 假阴性：报错了但 Blender 代码没问题
}

换成构造器注入，这个测试根本编译不过。错误从"运行时的莫名 NPE"提前到了"编译错误"。

书里还有一个更完整的 UnsafeObject 例子，值得原样搬过来。它同时暴露了 setter 注入的所有失败模式：

public class UnsafeObject {
    private Slippery slippery;
    private Shady shady;
    public UnsafeObject() { }
    public void setSlippery(Slippery s) { this.slippery = s; }
    public void setShady(Shady s)       { this.shady = s; }
    public void init() { ... }        // 还必须记得调这个
}

下面每一种配置都能通过启动，每一种都有问题：

  1. 两个依赖都没设 → 第一次使用就崩；
  2. 只设了 slippery → 用到 shady 才崩，更危险（用 slippery 的路径一直正常）；
  3. 两个都设了但忘了 init-method → 可能永远不报错，只是行为不对；
  4. 全设对了、init 也配了 → 但 Spring 的 bean 默认是单例，多线程并发访问，非 final 非 volatile 字段的可见性无保证；
  5. 只好把三个 bean 全标成 scope="prototype" —— 为了一个随意的设计选择，付出了一整套配置代价。

构造器版本：

public class SafeObject {
    private final Slippery slippery;
    private final Shady shady;

    @Inject
    public SafeObject(Slippery slippery, Shady shady) {
        this.slippery = slippery;
        this.shady = shady;
        init();                       // 初始化在构造器末尾，private，无法被误调
    }
    private void init() { ... }
}

上面五个问题全部消失。只有一个构造器 → 只有一种构造方式；字段 final → 安全发布；init 私有且在构造器内 → 不可能忘、不可能重复调。

第 3 轮：可读性 —— setter 胜

参数多且同类型时，构造器是灾难：

public Spy(String name1, String name2, String name3) { ... }

new Spy("John Doe", "James Bond", "Don Joe");   // 顺序错了也编译通过

setter 版本一目了然：spy.setBritishAlias("James Bond")。2026 年这一轮翻盘了——见本章末的现代对照。

第 4 轮：构造器金字塔 —— setter 胜

同一个类在不同场景用不同的依赖子集（书里的例子是两栖动物：水里用鳃，陆上用肺）：

public Amphibian(Heart heart, Gills gills) { ... }   // 水生
public Amphibian(Heart heart, Lungs lungs) { ... }   // 陆生

再多几个"剖面"，构造器就堆成金字塔了，而且它们无法用名字区分。但作者立刻补了一刀：

作者的态度

"需要一个对象有多个剖面的场景很罕见，多半只出现在遗留代码或密封的第三方代码里。如果你经常遇到构造器金字塔，你该先认真质疑自己的设计，而不是宣布 setter 注入是解药。"

第 5 轮：循环引用 —— setter 胜（但有更好的办法）

Host 依赖 Symbiote，Symbiote 依赖 Host。两个都用构造器注入的话，先造谁都不行。三角、四角乃至任意长度的环也一样。

无解的那一种：in-construction 问题

如果环里的对象在构造/初始化过程中就要调用对方：

public class SymbioteImpl implements Symbiote {
    private final Host host;
    private final int hostAge;

    @Inject public SymbioteImpl(Host host) {
        this.host = host;
        this.hostAge = host.calculateAge();   // 代理还没拿到 delegate → 炸
    }
}

改用 setter 注入，能救一半：只要只有一边在初始化时调对方就行。如果双方都在初始化时调对方——

⚠ 无解

"构造器注入解决不了这个循环初始化的烂摊子。setter 注入同样解决不了。"

作者的出路是：这本来就不是接线问题，而是"把对象置于可用状态"的问题。用生命周期回调解决——先把所有对象接线完毕，再统一发一个"初始化"事件。见第 7 章。

今天就是 @PostConstruct：Spring/Jakarta 保证它在全部依赖注入完成之后才调用，这正好是作者当年缺的那个钩子。

结论

作者的裁决

"字段可变性和 setter 注入对'意外的无效构造'的脆弱，代价太大，无法忽视。永远先试构造器注入，只在不得不的时候退回 setter 注入。"

3.3依赖来得太晚：三种部分注入模式

有时候你在构造时拿不到全部依赖，或者依赖用一次就废了。奶奶吃苹果：

public class Granny {
    private final Apple apple;
    public Granny(Apple apple) { this.apple = apple; }

    public void eat() {
        apple.consume();
        apple.consume();   // 苹果已经吃掉了 → 出错
    }
}

长命的宿主（Granny）依赖短命的服务（Apple）。这类问题有三种解法，能力递增：

Provider

public class Granny {
    private final Provider<Apple> appleProvider;

    @Inject public Granny(Provider<Apple> p) { this.appleProvider = p; }

    public void eat() {
        appleProvider.get().consume();     // 每次 get() 一个新苹果
        appleProvider.get().consume();
    }
}

作者强调 Provider 和服务定位器的两个区别：它是类型专属的（不用强转），它只有一个方法（get()，唯一职责是按作用域提供实例）。Guice 对所有绑定类型开箱提供 Provider<T>；Spring 那个年代要自己写一个实现 BeanFactoryAware 的类。

Assisted Injection

依赖需要一个只有在使用时才知道的上下文参数（比如"当前这期通讯稿"）：

public class Deliverer {
    private final Newsletter letter;
    private final MailServer server;          // 这个由容器注入

    @Inject public Deliverer(@Assisted Newsletter letter, MailServer server) {
        this.letter = letter;  this.server = server;
    }
}

public interface DelivererFactory {           // 只写接口，实现由容器生成
    Deliverer forLetter(Newsletter letter);
}

关键价值：既保住了构造器注入（final、有效性），又能传运行时参数。如果自己手写工厂 return new Deliverer(letter)，就退回了手工构造——失去病毒式注入、拦截、作用域。

Builder

上下文超过一个时，Assisted 的类型签名开始失控（TwoAssistsProvider<T,C1,C2>、ThreeAssists…）。Builder 用方法调用代替类型参数：

builder.letter(letter);
builder.mailServerUrl("mail.wideplay.com");
builder.port(21);
Deliverer d = builder.buildDeliverer();

Builder 自己也可以被注入依赖，从而在构建时做转换：

public Deliverer buildDeliverer() {
    MailServer server = finder.findMailServer(mailServerUrl, port);   // finder 是注入的
    return new Deliverer(letter, server);
}

Builder 还能隐藏实现选择——builder.buildRedApple() / buildGreenApple()，客户端只知道 Apple，永远看不到 RedApple/GreenApple。用 Provider<RedApple> 就做不到这一点，它把实现类型泄漏给了客户。

⚠ Builder 要复用就必须重置 
public Deliverer buildDeliverer() {
    try {
        return new Deliverer(letter, mailServerUrl, port);
    } finally {
        letter = null;  mailServerUrl = null;  port = -1;   // 失败的构建不污染下一次
    }
}

更稳妥的做法：每次通过 Provider 拿一个新 Builder，杜绝复用和并发使用。

3.4密封代码：改不了源码怎么办

第三方库以二进制形式提供，你没法加注解、没法重构。三种手段：

  1. 外部元数据。XML 配置天然不需要碰源码；Guice 也可以 bind(Sealed.class).toConstructor(...) 直接绑到某个构造器上。
  2. 工厂方法。Spring 的 factory-method="newInstance" 能把静态工厂方法当构造器用。
  3. Adapter。最强的一招——继承它，在子类里做接线：
public class SealedAdapter extends Sealed {
    @Inject
    public SealedAdapter(Dependency dep1, Dependency dep2, Dependency dep3) {
        super(dep1);          // 调用非 public（但非 private）的构造器
        dependOn(dep2);       // 调用命名不合规范的 setter
        relyOn(dep3);
    }
}

Adapter 的四个好处：基础设施逻辑被干净地封在 Adapter 里；拼写错误编译期就发现；Sealed 的所有客户端一行都不用改；测试方式和原类一样。

4.1模块是什么

4.3测试：单元 vs 集成

作者的立场很硬：没有经过形式化验证的代码，价值近乎为零。手工点点菜单不算测试，它漏掉了坏数据、并发瓶颈这些看不见的失效点。

out-of-container 单元测试

public class BookCatalogTest {
    @Test public void freeFormSearch() {
        MockLibrary mock = new MockLibrary();
        new SimpleBookCatalog(mock).search("dependency injection");
        assert mock.foundByKeyword();
    }
}

注意：这里用的是手工构造，没有注入器。依赖只有一两个，全是 mock，为几个 mock 去配一个注入器纯属自找麻烦。

⚠ 反模式："我真的需要我的依赖" 
public class BookCatalogTest {
    private Injector injector;

    @BeforeMethod public void setup() {
        injector = Guice.createInjector(new TestBooksModule());   // 只为测试而存在的配置
    }

    @Test public void freeFormBookSearch() {
        new SimpleBookCatalog(injector.getInstance(Library.class)).search("..");
    }
}

三宗罪：① 测试多了一个对注入器的依赖；② TestBooksModule 是纯粹为测试维护的、不产生价值的代码；③ 注入器配置一旦出错，测试报的是假阴性——你会花几小时在错误的地方找 bug。

作者的判据非常好用："当你发现某个类的依赖没法被 mock 掉，你该重新考虑设计。"

mock 不只是替身，还是行为断言

验证一个类的行为，一半在返回值，另一半在它怎么使唤自己的依赖。这里必须用行为脚本：

@Test public void freeFormBookSearch() {
    Library mock = createStrictMock(Library.class);   // strict = 顺序也要对
    String criteria = "dependency injection";

    expect(mock.findByAuthor(criteria)).andReturn(null);    // 先按作者
    expect(mock.findByKeyword(criteria)).andReturn(null);   // 再按关键字
    Book di = new Book("dependency injection");
    expect(mock.findByTitle(criteria)).andReturn(di);       // 最后按标题

    replay(mock);
    Book result = new SimpleBookCatalog(mock).search(criteria);
    verify(mock);                                // 断言调用方式和顺序
    assert di.equals(result);                    // 断言返回值
}

如果实现改成"优先按标题搜"，这个测试会失败——调用顺序本身就是行为的一部分。

集成测试

集成测试关心的是"拼起来对不对"，所以它可以且应该违反上面那些单元测试规则：

public class HomePageIntegrationTest {
    private Injector injector;

    @BeforeTest public void prepareContainer() {
        injector = Guice.createInjector(new WebModule(),          // 生产模块
                                        new TestPersistenceModule()); // 只有环境差异走替身
    }
    @AfterTest public void cleanup() { ... }

    @Test public void renderHomePage() throws Exception {
        injector.getInstance(HomeServlet.class).service(mockRequest, mockResponse);
    }
}

五条原则：尽量用生产模块；只把环境差异（数据库实例等）抽出来做平行配置；外部交互靠模拟（HTTP 请求）；启动昂贵，所以用 @BeforeTest 只跑一次；必须有 cleanup() 关闭外部资源。

一个很好的判据

"在一个健康的代码库里，集成测试应该很少失败。它揭示的通常是配置怪癖和库的互操作问题，而不是编码错误——那些应该被单元测试覆盖掉。"

如果你的集成测试天天挂在业务逻辑上，说明单元测试覆盖不足。

4.4运行时重绑定

最后一节讲一个高级（且危险）的用法：运行时改变对象图的结构。作者先泼冷水：

⚠ 先读这段警告

"在运行时修改注入器配置和对象模型有潜在危险。没有仔细的库支持，你会失去启动时的校验与安全特性，可能导致不可预测、不稳定、甚至无法检测的 bug。"

五条约束：绑定一旦建立就持续生效直到重绑；已经持有旧实例的对象不会更新；重绑与作用域强相关（长命对象拿着被重绑的键就必须重注入或丢弃）；重绑与生命周期强相关（依赖变更需要通知相关模块）；不是所有注入器都支持。

朴素做法是把两条依赖都注入进去然后用 flag 切换——但这就把基础设施逻辑混进了业务类。Adapter 又一次救场：

public class DependencyAdapter implements Dependency, Rebindable {
    private final DependencyA a;
    private final DependencyB b;
    private boolean useA = true;

    public void rebind()   { useA = false; }
    public int calculate() { return useA ? a.calculate() : b.calculate(); }
}

于是客户端回到干净状态：

public class LongLived {
    private final Dependency dep;     // 只认契约，重绑完全透明
    @Inject public LongLived(Dependency dep) { this.dep = dep; }
    public void go() { int r = dep.calculate(); ... }
}

注意 Rebindable 这个角色接口：控制逻辑只需维护一个 Rebindable 列表，逐个通知即可。这就是第 7 章"多播生命周期"的雏形。

第 5 章

作用域：状态的容器

这是让注入器区别于服务定位器的那个特性。作用域是一个键所对应的实例保持同一的时间段。把状态的归属声明出来交给容器管理，业务代码就可以对"当前是谁的请求"这件事一无所知——而这正是它该有的样子。

  • no scope / prototype
  • singleton scope
  • 绑定的是键，不是类
  • 单例反模式
  • request / session
  • guice-servlet

5.1牙膏的比喻

作者用一家人刷牙来定义作用域，这个比喻好用到值得原样引进：

family.give("Joanie", injector.getInstance(Toothpaste.class));
family.give("Jackie", injector.getInstance(Toothpaste.class));
family.give("Sachin", injector.getInstance(Toothpaste.class));

代码一个字都不用改，但语义完全取决于 Toothpaste 被绑到什么作用域：

  • 单例作用域 = 全家共用一个浴室、一支牙膏。Sachin 最后刷，可能已经没牙膏了。
  • 无作用域 = 一人一个浴室、一支新牙膏。谁都不会被挤掉。

这就是作用域的全部价值：同样的调用，不同的状态语义，而调用方不知情。

它带来四个好处：让注入器管理对象的潜在状态；确保服务按需拿到新的依赖；按上下文隐式隔离状态；减少业务代码里"状态感知"的逻辑——这一条最重要，它让代码好测也好推理。

5.2无作用域：一次一个新的

作者在这里做了一个很细的辨析。无作用域不对应任何概念上的上下文：如果 Sachin 刷两次牙，就会造出四支牙膏，而"三个浴室"的模型里只该有三支。所以严格说，

精确定义

无作用域的含义是：注入器每次查找这个键，都构造并接线一个全新实例。没有任何上下文承诺。硬要说，它是一个"上下文完全绑定在引用者身上的、一瞬间的作用域"。

命名差异：Guice / PicoContainer 叫它默认作用域 / 无作用域；Spring 叫 prototype（键是"创建新对象的模板"）。

5.3单例作用域

单例的上下文就是注入器本身。一个注入器一个实例。注意这句话的限定语——

⚠ 最常见的误解

很多人以为单例意味着"整个应用一个实例"。在 DI 里不是。同一个应用里可以有多个注入器，每个注入器持有自己的一份单例。PicoContainer 干脆放弃了 singleton 这个词，改叫 cache scoping。

什么该是单例

  • 客户的汇聚点：数据库连接池——所有要连库的服务都要经过它。
  • 无状态服务：业务 API（PersonnelManager、SalaryManager）本身没有状态，只有不可变的数据访问依赖。此时单例比无作用域更优：可以启动时预建（省掉运行时构造开销）、调试时只有一个引用点、内存占用是常数而非线性。

什么不该只因为"贵"就设为单例——这一段作者写得很克制，值得抄下来：

别为了性能而单例

对象图大、依赖慢速外部资源、构造后要做昂贵计算——这些本身都不构成理由。该问的是上下文问题。数据库连接池设计上就该长期持有 → 单例合理。但一个 TCP socket，虽然建立昂贵，如果用户可能登出再登入到另一台服务器，那就是新的上下文，必须新实例。

"在没有看到明确的性能短板之前，别急着把对象优化成单例。这句话你可以在每次开始猜测和担心性能时对自己重复一遍。"

5.5Web 作用域：请求与会话

⚠ 这里为什么必须用 Provider

⚠ 使用 Web 作用域的四条注意
  • 一个请求通常独占一个线程 → 请求作用域对象一般不需要线程安全，也一般不是线程安全的；
  • 但会话作用域不一样：同一个用户的多个并发请求会同时命中同一个会话实例；
  • 集成层通常把作用域实例缓存在 ThreadLocal 里 → 请求结束必须清理；
  • 少数情况下服务器会用多个线程服务一个请求（长轮询/异步），此时 ThreadLocal 的假设会崩。

6.1动手造一个事务作用域

动手之前先回答三个问题。作者把它们放在最前面，是有道理的——第二个问题几乎是所有自定义作用域事故的根源：

  1. 这个作用域代表的上下文是否定义清晰？（起点在哪、终点在哪）
  2. 对象必须活满整个作用域——对该作用域里的每一个键都成立吗？绝不能在一个作用域里出现两种寿命。
  3. 会不会有多个线程访问这个作用域里的对象？

事务（ACID：原子、一致、隔离、持久）恰好三条全过：起止明确（begin/commit），寿命一致，且通常限定在单线程内。

为什么需要它：核电站的例子

public class PowerStation {
    public void start() {
        transaction.begin();
        boolean failed = false;
        try {
            chamber1.fire();  chamber2.fire();  chamber3.fire();
        } catch (StartFailedException e) {
            failed = true;
        } finally {
            if (failed) transaction.rollback(); else transaction.commit();
        }
    }
}
public class Chamber {
    private final Gauge gauge;
    public void fire() {
        gauge.measure();
        if (gauge.temperature() > 100) throw new StartFailedException();
    }
}

需求是三个燃烧室的温度之和不能超过 100。现在 Gauge 是无作用域的，每个 Chamber 各有一个仪表，量的是各自的温度——需求实现不了。

那设成单例？也不对——那样连备用燃烧室、连根本不是燃烧室的组件都会共享这个仪表。正确的上下文是"这一次启动"，也就是这个事务。于是：

@TransactionScoped
public class Gauge { ... }

PowerStation、Chamber 和它们的方法一行都不用改。这就是作用域的威力：换一个词，语义全变，业务代码毫不知情。

Scope 接口只有一个方法

public interface Scope {
    <T> Provider<T> scope(Key<T> key, Provider<T> unscoped);
}

两个参数的含义是理解自定义作用域的钥匙：key 是要被作用域化的键；unscoped 是一个"无作用域的 provider"——当上下文里还没有这个实例时，用它造一个新的。

Guice 实现

public class TransactionScope implements Scope {
    private final ThreadLocal<Map<Key<?>, Object>> instances = new ThreadLocal<>();

    public <T> Provider<T> scope(final Key<T> key, final Provider<T> unscoped) {
        return new Provider<T>() {
            public T get() {
                Map<Key<?>, Object> map = instances.get();
                if (null == map)
                    throw new OutOfScopeException("no transaction was active");
                if (!map.containsKey(key)) map.put(key, unscoped.get());
                return (T) map.get(key);
            }
        };
    }

    public void beginScope() { instances.set(new HashMap<>()); }
    public void endScope()   { instances.remove(); }
}

那个加粗的检查非常重要。在事务之外请求事务作用域的对象，说明程序逻辑或配置有错。如果不检查，你会得到一个空指针或者更糟的静默错误，然后花几小时在错误的地方找 bug。

注册：

bindScope(TransactionScoped.class, new TransactionScope());

@Retention(RetentionPolicy.RUNTIME)
@ScopeAnnotation                       // 元注解：告诉容器这是个作用域注解
public @interface TransactionScoped { }

6.2陷阱一：单例必须线程安全

⚠ 没有例外

"Singletons absolutely must be thread-safe — no exceptions."

两条路。首选不可变：

@Immutable @Singleton
public class MySafeObject {
    private final Dependency dep1;
    private final Dependency dep2;
    @Inject public MySafeObject(Dependency d1, Dependency d2) { ... }
    // 没有 setter，没有能改变依赖状态的方法
}

做不到不可变时（比如为了破循环引用而用了 setter），退而求其次用 volatile：

安全
@ThreadSafe @Singleton
public class MySafeObject2 {
    private volatile Dependency dep1;
    private volatile Dependency dep2;

    @Inject public void set(Dependency d1, Dependency d2) {
        this.dep1 = d1; this.dep2 = d2;
    }
}
致命
@NotThreadSafe @Singleton
public class MyUnsafeObject {
    private Dependency dep1;      // 非 final 非 volatile
    private Dependency dep2;

    @Inject public void set(Dependency d1, Dependency d2) {
        this.dep1 = d1; this.dep2 = d2;
    }
}

右边为什么致命：Java 语言对非 final、非 volatile 字段在线程间的可见性不做任何保证。设置它的那个线程能看到值，别的线程可能永远看不到。JVM 允许每个线程持有本地缓存副本。第 9 章会详细展开。

作者对线程安全的态度值得抄下来："不存在能判定一个类完全线程安全的试金石。仔细推理它的线程环境；探索常见和非典型的使用场景；试着说服至少一个别人；主动寻找缺陷，永远不要假设它们不存在；验证你的每一个假设。测试，测试，再测试。"

6.3陷阱二：作用域越界注入（scope-widening）

本章的核心。把窄作用域的对象注入进宽作用域的对象，被注入的那个就脱离了自己作用域的管辖——上下文结束了，它还活着。

作者特别提醒：越界不限于"窄 vs 宽"，同一个作用域的两个不同上下文之间也算（比如两个用户会话被一个单例桥接起来）。

事故 A：静默的错误结果

@Singleton
public class TextReader {
    private final WordCounter counter;     // WordCounter 是无作用域的

    public void scan(List<String> strings) {
        for (String s : strings) counter.count(s);
        System.out.println("Total words: " + counter.words());
    }
}

每次调用都传 7 个词，期望每次都打印 7。实际输出：

Total words: 7
Total words: 14
Total words: 21

两种修法：

  • 降低宽的那个的作用域——把 TextReader 也改成无作用域。最简单，但不总是可行。
  • 注入 Provider——第 3 章的重注入模式，本质上 scope-widening 就是重注入问题的一种形态。
⚠ 用了 Provider 也可能出错 
public void scan(List<String> strings) {
    for (String s : strings) counterProvider.get().count(s);       // 每个词一个新计数器
    System.out.println("Total: " + counterProvider.get().words()); // 又一个新的 → 永远打印 0
}

正确写法是每个方法调用取一次：WordCounter counter = counterProvider.get(); 然后复用它。作者说得很实在：这种错误"多半会让你满世界找 bug，就是不会想到作用域上"。

事故 B：out-of-scope 对象

把 servlet 标成请求作用域：

@RequestScoped
public class HelloServlet extends HttpServlet {
    public void init(ServletConfig config) { ... }    // 容器启动时调用
}

Web 应用启动时 init() 被触发，此时没有任何活动请求 → OutOfScopeException → 整个应用起不来。会话作用域同理。

解法是第 3 章的 Adapter：用一个单例包住它，把"生命周期方法"留在单例里，把"请求内的方法"委托下去：

@Singleton
public class HelloServletAdapter extends HttpServlet {
    private final Provider<HelloServlet> delegate;

    public void init(ServletConfig config) { /* 初始化逻辑留在这一层 */ }

    public void service(HttpServletRequest req, HttpServletResponse res) {
        delegate.get().service(req, res);    // 这里一定在请求内，安全
    }
}

事故 C：线程安全

单例的窄作用域依赖，会被单例的所有调用线程碰到。

@Singleton
public class TextPrinter {
    private final Counter counter;                // @NotThreadSafe

    public void print(String text) {
        System.out.println(text);
        counter.increment();
        if (counter.getCount() == 100) System.out.println("done!");
    }
}

问题分两层。第一层是可见性：count 非 volatile，各线程看到的值不一致。加了 volatile 之后还有第二层——两个线程可能一个把计数推到 100、另一个推到 101，然后两个都跳过了 == 100 的判断，"done!" 永远不打印。

解法是互斥：

@ThreadSafe @Singleton
public class TextPrinter {
    public synchronized void print(String text) { ... }   // 由持有者负责加锁
}

注意 Counter 本身仍然标注 @NotThreadSafe——因为它作为一个组件依然可以被不安全地使用。责任在持有它的单例身上。

事故 D：内存泄漏

@Singleton
public class BadServlet extends HttpServlet {
    public final List<WebPage> pages = new ArrayList<>();     // 单例持有，永不释放

    public void service(HttpServletRequest req, HttpServletResponse res) {
        pages.add(page.get());                              // 每个请求攒一个
        pages.get(0).handle(req, res);
    }
}

单例活到应用关闭，所以它引用的一切都活到应用关闭。不停刷新这个 URL，最终 OutOfMemoryError。改法很简单——用完就丢：

public void service(HttpServletRequest req, HttpServletResponse res) {
    page.get().handle(req, res);     // 不保存引用，GC 可以回收
}
⚠ 四类事故的共同点

它们全都测不出来。单元测试测不出（每个类都是对的），集成测试也不可靠（并发和内存问题需要特定负载才显形）。作者给出的唯一防线是设计纪律：

  • 让整个对象图绑在最窄的作用域上；
  • 必须跨作用域时，用 Provider 或 Adapter；
  • 想清楚并说服另一个人；

① 手写 ThreadLocal 作用域：换成 ScopedValue

6.1 节那份 TransactionScope 的核心是 ThreadLocal<Map> + 手动 begin/end。它有两个已知弱点：忘了 endScope() 就在线程池里泄漏；子线程看不到上下文。Java 25 的 ScopedValue（JEP 506）两个都解决了：

static final ScopedValue<Map<Key<?>, Object>> TXN = ScopedValue.newInstance();

ScopedValue.where(TXN, new HashMap<>()).run(() -> {
    txn.begin();
    try { chamber1.fire(); chamber2.fire(); chamber3.fire(); txn.commit(); }
    catch (StartFailedException e) { txn.rollback(); }
});   // ← 出了这个块，上下文自动消失，没有 remove() 可以忘

构造。内存分配完成后调用构造器，做初始化。第 3 章已经论证过，把依赖接线和初始化计算都放这里是最好的：

}

终结。C++ 有析构函数，Java 有 finalize()。但两者的语义天差地别：

⚠ finalizer 不能用来释放有限资源

Java 只保证 finalizer 在对象被回收之前运行。它可能很早很频繁，也可能很晚很稀少，可能要等到应用关闭才跑，也可能根本不跑（应用异常退出）。

public class Thumbnail {
    private InputStream data;

    public Image display(String path) throws IOException {
        data = fileSystem.getPath(path).newInputStream();   // 打开文件
        ...
    }

    @Override protected void finalize() throws Throwable {
        data.close();          // ← 永远不知道什么时候执行
        super.finalize();
    }
}

用户翻几十张图，几十个文件句柄同时开着，很容易耗尽操作系统资源——而它们其实早就不用了。

finalizer 的两个合法用途：

  • 兜底检查——不是替代关闭，而是发现"忘了关"： 
    @Override protected void finalize() throws Throwable {
    if (null != data) {
        logger.warning("unclosed thumbnail: " + this);   // 报警
        data.close();
    }
    super.finalize();
}
  • 释放非托管内存——调用本地方法释放 C 库持有的内存。

Spring 和 PicoContainer 都提供一个"应用关闭时调用"的通用销毁钩子：

    <constructor-arg ref="fileSystem"/>

看起来比 finalizer 强，但对 Thumbnail 来说问题一模一样：文件句柄要一直开到应用退出。正确做法是"每张图预览完就关"，而通用 destroy 钩子表达不了这件事。

作者还指出两个额外问题：

  • 销毁顺序不确定。ZipFileSystem.close() 和 Thumbnail.close() 谁先跑？如果一个在关闭时还需要另一个，就会撞上"依赖已经关了"的非法状态。于是你被迫写这种防御性代码： 
    public void close() {
    if (null != reader) {
        if (reader.isOpen()) reader.someLastMinuteLogic();   // 扭曲且不必要
        reader = null;
    }
    shutdownMyself();
}
  • 误用泛滥。作者见过给 Java Swing 窗口写"析构函数"来释放控件的——而 Swing 控件是托管内存，根本不需要手动释放。
替代方案：领域相关的终结契约

把"可关闭"做成类型性质，而不是外部配置。java.io.Closeable 的文档说得很清楚："Closeable 是一个可以被关闭的数据源或目的地。"

@ThreadSafe
public class ResourceCloser implements Runnable {
    @GuardedBy("lock") private final List<Closeable> toClose = new ArrayList<>();
    private final Object lock = new Object();

    public void schedule(Closeable resource) {          // 用完的资源排队
        synchronized (lock) { toClose.add(resource); }
    }
    public void run() {                                 // 低优先级线程周期性关闭
        synchronized (lock) { for (Closeable r : toClose) r.close(); }
    }
}

这样关闭时机由业务语义决定，而不是由"应用什么时候退出"决定。

7.6自定义生命周期：后处理与多播

public class Screen {
    private final Feed daytimeFeed;
    private final Feed overnightFeed;

    public void suspend() { show(overnightFeed); }
    public void resume()  { show(daytimeFeed); }
}

做法一：后处理（Spring BeanPostProcessor）

public class LifecyclePostProcessor implements BeanPostProcessor {
    private final List<Screen> screens = new ArrayList<>();

    public Object postProcessAfterInitialization(Object object, String key) {
        if (object instanceof Screen) screens.add((Screen) object);   // 登记
        return object;                                                  // 原样返回
    }

    public void suspendAllScreens() {           // 定时器午夜调用
        for (Screen s : screens) s.suspend();
    }
}

收益：不用给每块屏写一个定时器，也不用让 Screen 自己关心时间。一个生命周期管理器，更少代码、更少测试、更少故障点。

做法二：多播（PicoContainer Gems）

把类的能力表达成角色接口（回到第 3 章的接口注入思想）：

public class Screen implements Suspendable, Resumable { ... }

public interface Suspendable { void suspend(); }
public interface Resumable   { void resume(); }
public void suspendAll() {
    Suspendable target = (Suspendable) Multicaster.object(
            injector, true, new StandardProxyFactory());   // 动态生成的多播代理
    target.suspend();      // 一次调用，转发给容器里所有 Suspendable
}

① finalize()：从"不推荐"变成"正在被删除"

作者当年只是警告别滥用。之后的历史更激烈：

版本发生了什么
Java 7 (2011)AutoCloseable + try-with-resources —— 确定性释放有了语法支持
Java 9 (2017)Object.finalize() 标记为 @Deprecated；引入 java.lang.ref.Cleaner 作为替代
Java 18 (2022)JEP 421：终结机制标记为"将被移除"；可用 --finalization=disabled 提前关掉
今天新代码里写 finalize() 等于写错

作者说的那两个"合法用途"，现代对应物是：

// 用途一「兜底 + 报警」→ try-with-resources 让你根本不会忘
try (InputStream data = fileSystem.newInputStream(path)) {
    return renderThumbnail(data);
}   // 出块即关，异常也关。7.1 节整个问题消失

// 用途二「释放本地内存」→ Cleaner（不是 finalize）
class NativeBuffer implements AutoCloseable {
    private static final Cleaner CLEANER = Cleaner.create();
    private final Cleaner.Cleanable cleanable;

    NativeBuffer(long addr) {
        this.cleanable = CLEANER.register(this, () -> freeNative(addr));
        // 注意：lambda 里不能捕获 this，否则对象永远不可达回收
    }
    public void close() { cleanable.clean(); }
}

更彻底的方案：Java 22+ 的 Foreign Function & Memory API（Arena）把本地内存的生命周期也做成了 try-with-resources。

原书批评通用 destroy-method 有两点：时机不对、顺序不确定。Spring 后来补了两个机制：

@Bean(destroyMethod = "close") DataSource ds() { ... }

// 阶段化启停：SmartLifecycle 让你显式指定顺序
@Component
class MessageListener implements SmartLifecycle {
    public int getPhase() { return 100; }        // phase 小的先启动、后停止
    public void start() { ... }
    public void stop()  { ... }                  // 优雅停机时按 phase 逆序调用
}

但核心批评依然成立：destroy-method 适合"跟应用同生共死的资源"（连接池、线程池、消息监听器），不适合"用一次就该关的资源"（Thumbnail 的文件流）。后者永远该用 try-with-resources。

⑤ 懒 / 饿加载

  • Spring Boot 2.2+ 支持全局懒加载：spring.main.lazy-initialization=true。用于加快开发期启动，不建议用于生产——它把"启动失败"推迟成了"运行时失败"。

但请注意：模型消失了，问题没消失。把购物车存进 Redis、下次请求再取出来并"刷新可能变化的价格"——这就是 @PrePassivate/@PostActivate 干的事，只是你现在手写它。

            txn.rollback();
        } finally {
            if (!txn.rolledBack()) txn.commit();
        }
    }
}
声明式

    }

右边发生的事情叫织入（weaving），被插入的行为叫通知（advice）。织入有三个时机：

Guice 的拦截器

public class TracingInterceptor implements MethodInterceptor {   // AopAlliance 接口
    public Object invoke(MethodInvocation mi) throws Throwable {
        System.out.println("enter " + mi.getMethod().getName());
        try {
            return mi.proceed();               // 放行到真实方法
        } finally {
            System.out.println("exit " + mi.getMethod().getName());
        }
    }
}
bindInterceptor(any(), any(), new TracingInterceptor());
//              ↑类匹配器  ↑方法匹配器

注意 finally：异常也要保证出口日志被打印。这是拦截器的基本纪律。

<aop:config>

                      expression="execution(* example.*.*(..))" />
        <aop:around pointcut-ref="pointcuts.anyMethod" method="trace"/>

⚠ 单元测试抓不到这个

8.2两个真实用例

声明式事务

没有拦截时，每个方法都要写这一坨：

public void newCar(Car car) {
    EntityTransaction txn = em.getTransaction();
    txn.begin();
    boolean succeed = true;
    try { em.persist(car); }
    catch (RuntimeException e) { txn.rollback(); succeed = false; }
    finally { if (succeed) txn.commit(); }
}

加上 @Transactional 后剩下：

@Transactional
public void newCar(Car car) { em.persist(car); }

作者特意点出一个容易被忽略的收益：上面那段手写代码把异常吞掉了（catch 之后什么都没做）。声明式事务除了省样板，还把"什么异常该回滚"变成了框架统一的、正确的语义。

方法级安全

<security:global-method-security>
    <security:protect-pointcut
        expression="execution(* example.PhoneService.*(..))"
        access="ROLE_ADMIN" />
</security:global-method-security>

拦截器在方法执行前校验当前用户的角色，不够就抛异常——目标方法根本不会执行。这是拦截器相对于"在方法开头写一行检查"的关键优势：它能阻止调用，而且这个策略是集中声明的。

8.3代理的五条边界

本章最有价值的一节。记住一句话就够了：代理只是一个子类。凡是子类不能覆盖的东西，代理都拦不到。

边界 1：相同性判断不可靠

final Painting picasso = new Painting("Picasso");
Injector injector = Guice.createInjector(... bind(Painting.class).toInstance(picasso) ...);

assert picasso == injector.getInstance(Painting.class);   // 失败！拿到的是代理

两个常见的连带错误：

会拿到代理的类名
public class ANoisyService {
    public final Logger log =
        Logger.getLogger(getClass().getName());
    // 可能打印成 ANoisyService$$EnhancerByCGLIB$$…
}
显式写死类字面量
public class ANoisyService {
    public final Logger log =
        Logger.getLogger(ANoisyService.class.getName());
}
把代理排除在相等之外
public boolean equals(Object o) {
    if (o == null ||
        o.getClass() != EqualToNone.class) return false;
    ...
}
用 instanceof
public boolean equals(Object o) {
    if (!(o instanceof EqualToNone)) return false;
    ...
}

边界 2：静态方法

Java 的静态方法不能被覆盖，只能被隐藏。作者做了一个很好的实验：子类定义同名 static 方法，从子类里调用会用子类版本，看起来像"覆盖"——但那只是词法作用域的效果。从外部调用必须显式指明是哪一个。结论：需要动态行为的逻辑，不要放在静态方法里。

边界 3：私有方法

把 clean() 改成 private，拦截器就完全看不到它了。解法是提升可见性：

可见性能被代理？说明
private✗子类不可见
包级（无修饰符）✓推荐：包外完全不可见，但代理通常生成在同包下
protected✓对同层级以外隐藏，但其他模块的子类仍能看到
public✓全开放

边界 4：final 方法与 final 类

final 不是可见性修饰符，但它同样阻止覆盖。类是 final 时连子类都生成不了。解法是委托：

class FrenchChefDelegator implements Chef {
    private final FrenchChef delegate;                // 组合而非继承
    public void cook()  { delegate.cook(); }
    public void clean() { delegate.clean(); }
}

作者的建议：拿不准就用组合，别用继承；更好的做法是直接代理接口。

边界 5：字段

AspectJ 的构建期织入能改字段，Spring AOP 和 Guice AOP 都不能。而且——

public class FrenchChef implements Chef {
    private final RecipeBook recipes = new RecipeBook();   // 手工构造
    public void cook() { recipes.read("ratatouille"); }
}

拦截器永远够不到 RecipeBook 的方法，因为它不是容器创建的。这句话反过来说更重要：任何你希望被拦截的依赖，都必须由注入器创建。手工 new 出来的对象自动退出 AOP 体系——这是第 1 章"别自己 new"的又一条理由。

拦截与测试

拦截让"单元行为"和"语义行为"分了家：TicketBooth.purchase() 的单元测试只知道它卖票；加了一个"每 100 位顾客打折"的拦截器后，系统的实际语义变了。作者的解法是纵向集成测试：

@Test public void discountEveryHundredthTicket() {
    Injector injector = Guice.createInjector(new AbstractModule() {
        protected void configure() {
            bind(TicketBooth.class);
            bindInterceptor(any(), any(), new DiscountingInterceptor());   // 装上真实拦截器
        }
    });
    TicketBooth booth = injector.getInstance(TicketBooth.class);
    for (int i = 1; i < 101; i++) {
        Ticket t = booth.purchase(Money.inDollars("200"));   // 走真实调用路径
        if (i == 100) assert t instanceof DiscountedTicket;
    }
}

"当程序里有依赖这类副作用的服务时，纵向集成测试提供的信心远大于各个单元测试之和。"

① 五条边界：全部成立，而且多了一条最常见的

自调用（self-invocation）——书里完全没提，但它是今天 Spring 用户踩得最多的坑：

@Service
public class OrderService {
    public void placeOrders(List<Order> orders) {
        for (Order o : orders) this.save(o);      // ← this 是真实对象，不是代理！
    }

    @Transactional
    public void save(Order o) { ... }               // 事务静默失效，一行报错都没有

9.1不安全发布

单线程下，写在前读在后，天经地义：

Map<String, Email> emails = new HashMap<>();
emails.put("Dhanji", new Email("dhanji@gmail.com"));
System.out.println(emails.get("Dhanji"));      // 词法顺序保证了正确性

加一个线程，这个保证就没了：

public class UnsafePublication {
    private Map<String, Email> emails = new HashMap<>();

    public void putEmails() {                          // 线程 A
        emails.put("Dhanji", new Email("dhanji@gmail.com"));
        System.out.println("Map updated.");
    }
    public void read() {                               // 线程 B
        System.out.println("… really is " + emails.get("Dhanji"));
    }
}

可能的输出：

Map updated.
Dhanji's email address really is null

作者做了一个很漂亮的加强：就算线程 A 自己在打印之后立刻读一遍，也可能出现这个结果：

Map updated.
Dhanji's email address really is dhanji@gmail.com    // 线程 A 自己读，正确
Dhanji's email address really is null                // 线程 B 读，null

同样的问题会直接出现在依赖注入上：

可能不安全
public class MoreUnsafePublication {
    private EmailDatabase service;      // 非 final

    public MoreUnsafePublication(EmailDatabase s) {
        this.service = s;
    }
    public void read() {
        service.get("Dhanji");          // 可能 NPE
    }
}
安全
public class SafePublication {
    private final EmailDatabase service;

    public SafePublication(EmailDatabase s) {
        this.service = s;
    }
    public void read() {
        service.get("Dhanji");          // 所有线程都保证看得到
    }
}
一行代码的价值

final 字段有语言级的可见性保证：只要构造器正常返回、且 this 没有在构造期间逃逸出去，任何线程都能看到它的正确值，不需要额外同步。

这也是第 3 章"构造器注入优先"最硬的技术论据——setter 注入的字段不能是 final，因此永远拿不到这个保证。

安全接线

有些容器会替你加同步（PicoContainer 的 LOCK 特性、Guice 对单例的保证）。但作者的态度很明确：

⚠ 不要依赖容器

"不要指望注入器来完成安全接线。如果你把类设计成在多线程环境下良好行为的，那它无论有没有库的帮助都是安全的。"三条理由：代码可以在不同环境复用；为并发做设计时需要这个性质；final 本身是意图的声明——别人读到就知道这里不该被改，手滑改了编译器立刻报错。

9.2哪些对象该交给注入器

作者说这是新手最容易走极端的地方：有人什么都用容器造，有人把容器当工厂只用一点点。判据其实很简单：

经验法则

凡是「服务」或「动作」组件，交给注入器；凡是「建模数据」的类，用手工构造。

封装：不是"藏起来"，是"别泄漏抽象"

作者举了一个非常干净的反例。消息服务：

抽象泄漏了
public interface Messager {
    void send(EmailMessage msg);   // 泄漏
}

class JabberMessager implements Messager {
    public void send(JabberMessage msg) { ... }
    // ← 编译不过：契约被 Email 绑架了
}
契约中立
public interface Messager {
    void send(Message msg);        // 中立
}

class JabberMessager implements Messager {
    public void send(Message msg) {
        JabberMessage j = convert(msg);   // 各自转换
        ...
    }
}

再进一步：把实现类彻底藏进包里。Java 有一个被严重低估的可见性级别——包级私有（不写任何修饰符）：

package example.messaging;

public interface Messager { void send(Message msg); }        // 唯一对外的东西

class JabberMessager implements Messager { ... }              // 包外不可见
class JabberTransport { ... }                                 // 包外不可见
class JabberMessageConverter { ... }                          // 包外不可见

public class MessagingModule extends AbstractModule {           // 加上一个配置类
    protected void configure() { bind(Messager.class).to(JabberMessager.class); }
}

这个包对外只暴露两样东西：一个单方法接口，一个模块。整个模块的 API 文档就是那一个方法。作者拿 warp-persist 的包结构举例，主包里只剩枚举、注解、接口和抽象类。

作者的经验法则

"凡是不属于接口、枚举、注解、抽象类的东西，都设成包级私有——因为这四种类型泄漏抽象逻辑的可能性最低。"

9.3五道不可变性谜题

作者把这一节写成了闯关题。建议你先自己答，再看解答。

谜题 1

public class Book {
    private String title;
    public String getTitle() { return title; }
    public void setTitle(String title) { this.title = title; }
}

不可变吗？不。有 setter。加 final + 构造器赋值即可。

谜题 2

public class AddressBook {
    private final String[] names;
    public AddressBook(String[] names) { this.names = names; }
    public String[] getNames() { return names; }
}

不可变吗？不。final 只锁住了引用，数组内容照样能改：

String[] names = book.getNames();
for (int i = 0; i < names.length; i++) names[i] = "Censored!";   // 合法且生效

作者的结论很直接：不要用数组，或者只在有明确保护和文档的前提下用。

谜题 3

public class BetterAddressBook {
    private final List<String> names;
    public BetterAddressBook(List<String> names) {
        this.names = Collections.unmodifiableList(names);
    }
    public List<String> getNames() { return names; }
}

不可变吗？看起来是——book.getNames().add(...) 会抛异常。

谜题 4（同一个类，换个用法）

List<String> physicists = new ArrayList<>(List.of("Landau", "Weinberg", "Hawking"));
BetterAddressBook book = new BetterAddressBook(physicists);

physicists.add("Einstein");        // 改的是原始列表

book.getNames();                     // → 四个人！

原来不是。unmodifiableList 只是一个视图，底层还是那个可变列表。修法是构造时复制：

@Immutable
public class BestAddressBook {
    private final List<String> names;
    public BestAddressBook(List<String> names) {
        this.names = Collections.unmodifiableList(new ArrayList<>(names));   // 防御性拷贝
    }
}

谜题 5

public class Library {
    private final List<Book> books;                              // Book 见谜题 1
    public Library(List<Book> books) {
        this.books = Collections.unmodifiableList(new ArrayList<>(books));
    }
    public List<Book> getBooks() { return books; }
}

字段 final、列表不可改、还做了拷贝。不可变吗？

library.getBooks().get(0).setTitle("The Tempest");            // 照样能改
不可变性的黄金律

一个对象要不可变，它的每一个依赖也必须不可变。前面 BestAddressBook 之所以侥幸成功，只是因为 Java 的 String 本身不可变。

9.4同步 ≠ 并发

不可变解决不了所有问题——有时候你就是需要共享的可变状态（计数器、缓存）。这时要区分两个目标：同步是让数据保持一致，并发是让线程不要排队。

计数器

同步：正确但会堵
public class MessageCounter {
    private int count = 0;

    public synchronized void messageReceived() {
        count++;
    }
}
// 每个线程都要抢锁、排队、放锁
// 线程一多就是瓶颈
并发：不排队
public class MessageCounter {
    private final AtomicInteger count =
        new AtomicInteger(0);

    public void messageReceived() {
        count.incrementAndGet();
    }
}
// 一条 CPU 原子指令，不可被打断

count++ 看起来是一个操作，实际是三个：读 → 加一 → 写回。中间任何一步都可能被别的线程插进来。incrementAndGet() 是硬件级原子操作，不会被打断，也不会阻塞别人。

缓存

全局一把锁
private final Map<String, Data> map =
    Collections.synchronizedMap(new HashMap<>());
// 每次 get() 都要拿锁
// 高流量下不可接受
并发容器
private final Map<String, Data> map =
    new ConcurrentHashMap<>();
// 读完全无锁
// 写只锁很小的局部

作者的收尾很好：用三道关卡处理并发问题——先问能不能不可变，再问是不是安全发布，最后才考虑并发数据结构。

2026 对照

① 一处需要修正的技术细节

书里说 ConcurrentHashMap 把键"分成若干条带（stripe），每条带一把锁"。这是 Java 5/6 的实现，Java 8 已经重写了。现在的实现是：读完全无锁（依赖 volatile 读）；写用 CAS，只有哈希冲突时才对单个桶加 synchronized。锁的粒度比"条带"更细，concurrencyLevel 构造参数也只剩兼容意义了。

结论方向完全正确，只是内部机制要更新。另外高竞争的纯计数场景，LongAdder 比 AtomicLong 更快（它内部分散热点，读时求和）。

② 五道谜题：record 干掉第一道，其余四道全部存活

// 谜题 1 消失：record 的字段天然 final，没有 setter
record Book(String title) {}

// 但谜题 2 依然存在！
record AddressBook(String[] names) {}          // ← 数组元素照样能改

// 谜题 5 也依然存在
record Library(List<Book> books) {}            // books 可以是可变列表；Book 若可变则更糟

// 正确写法：紧凑构造器里做防御性拷贝
record Library(List<Book> books) {
    Library {
        books = List.copyOf(books);            // 拷贝 + 不可变，一步到位（Java 10+）
    }
}

这是最值得强调的一点：很多人以为用了 record 就是不可变了。record 只保证浅层不可变——它自动通过第①关，②③④⑤四关还是要你自己过。

③ 不可变集合：终于有了一等公民

2009 年今天
Collections.unmodifiableList(new ArrayList<>(src))List.copyOf(src)（Java 10）—— 拷贝 + 真正不可变，一步完成
—List.of(...) / Map.of(...) / Set.of(...)（Java 9）
—Collectors.toUnmodifiableList()（Java 10）
Google Collections（书出版时刚起步）Guava ImmutableList —— 仍然是最全的一套

注意一个语义区别：List.of() 返回的是真正不可变的列表，不是"不可修改的视图"——谜题 4 那个漏洞在它身上不存在。

④ @Immutable：从注释升级为编译期检查

书里的 @Immutable（jcip-annotations）只是文档，"对程序语义没有影响"。今天有真会干活的版本：

@com.google.errorprone.annotations.Immutable        // Error Prone
record Library(ImmutableList<Book> books) {}
// ← 如果 Book 不是 @Immutable，编译期直接报错。
//    这正好把谜题 5 变成了编译器的工作

⑤ volatile 之外

9.1 节用 volatile 解决可见性，至今有效。补充两条：VarHandle（Java 9）提供了比 volatile 更精细的内存序控制（acquire/release/opaque），用于高性能库；final 字段的保证在 Java 9 之后随 JMM 的澄清而更加明确。但对绝大多数应用代码，作者的建议仍是最优解：优先不可变，其次 final，再次 volatile，最后才是锁。

⑥ 虚拟线程让这一章更重要了

Java 21 的虚拟线程把"开线程"的成本降到接近零，于是：

  • 共享可变状态被并发触碰的概率大幅上升——本章所有结论的权重都提高了；
  • synchronized 在早期虚拟线程实现里会"钉住"载体线程（pinning）造成吞吐损失，推荐改用 ReentrantLock（JDK 24+ 的 JEP 491 已消除大部分 pinning，但迁移建议仍在）；
  • 线程池不再是必需品 —— Executors.newVirtualThreadPerTaskExecutor()；
  • 结构化并发（StructuredTaskScope）让并发任务的生命周期跟代码块绑定，配合第 5、6 章说的 ScopedValue 传递上下文。

⑦ "服务 vs 数据"：判据没变，边界更清楚了

9.2 节的经验法则今天有了语法上的对应物：record 就是"数据对象"的语法标记。看到 record，你就知道它不该被注入、不该被 AOP 拦截（它是 final 的，见第 8 章）、不该有作用域。这大概是本书某条经验法则被语言层面认可得最彻底的一次。

⑧ 包级封装：依然是性价比最高的一招

作者那条"只把接口、枚举、注解、抽象类设为 public"的建议，今天有了更强的工具，但包级私有仍然是零成本、零依赖、立即可用的那一个：

  • JPMS（module-info.java）：模块级的 exports，比包级私有更强，但需要整个依赖链都模块化；
  • Spring Modulith：以包为模块边界，用测试来验证"没人越界访问内部包"；
  • ArchUnit：把这条规则写成测试。

顺带一提：作者截图展示的 warp-persist 包结构今天已经无法访问（项目停更），但那种"一个包只暴露一个接口 + 一个配置类"的组织方式，正是现代库设计的通行做法。

10.1web.xml：DI 的史前形态

看这段配置，它其实就是一个原始的注入器配置：

<servlet>
    <servlet-name>helloServlet</servlet-name>
    <servlet-class>com.wideplay.example.servlets.HelloServlet</servlet-class>
</servlet>

和 Spring 的 <bean id="…" class="…"/> 一模一样——只差一件事：它不允许你为 servlet 配置任何依赖。而任何一个真实的 Web 应用都有一堆依赖。这个"少一半"的设计，强加了四条限制：

  • servlet 必须有一个 public 的无参构造器；
  • servlet 类必须是 public 的具体类（不能是接口或抽象类）；
  • servlet 的方法无法被拦截（第 8 章的能力全部作废）；
  • servlet 实际上只能是单例。

后果就是：servlet 极难测试，于是一大批 Web 框架诞生出来绕开它，而每一个都自带一套自己的、部分的 DI 方案。作者列了一张表，今天读起来像一份考古报告——表里的框架大部分已经消失或边缘化，只有一件事留了下来：那种"各家自造轮子"的碎片化，是当年最真实的痛点。

作者对根因的判断很克制：不是框架作者水平不行，而是"可测试性、松耦合、作用域的价值，我们也是最近才学会的"——Guice 那时才两岁多。

10.2反模式一：刚性配置

框架都提供扩展点：你写一个小组件，实现框架的接口，插进去。问题出在怎么告诉框架用你这个插件。绝大多数 2009 年的框架用的是资源文件里的字符串：

# oscache.properties
cache.memory=false
cache.capacity=100
cache.persistence.class=com.opensymphony.oscache.plugins.diskpersistence.DiskPersistenceListener

前两行没问题——它们配的是值（数量、开关），字符串很合适。第三行不一样，它配的是一个类，也就是框架的一个依赖。于是三类失败接踵而至。

作者把最后这条单独点了名，因为它最阴险：

⚠ 静默失效

cache.persistance.class=...（persistence 拼错）—— 没有编译检查，没有运行时报错，连集成测试都通不过检查，因为 jokers.friend.is.batman=true 这种属性对资源文件来说也完全合法。

这直接导致了那个人人都干过的坏习惯：从上个项目或教程里复制粘贴一份"已知能跑"的配置。

10.3反模式二：黑盒 —— 脆弱基类

注意区分：封装是隐藏实现细节（好，第 9 章刚讲过）；黑盒是隐藏运作机制，让你既扩展不了也测试不了（坏）。作者挑了最常见的一种：用继承复用代码。

public class Queue<I> extends ArrayList<I> {
    private int end = -1;

    public void enqueue(I item) { super.add(0, item); end++; }
    public I dequeue() {
        if (end == -1) return null;
        end--;
        return super.get(end + 1);
    }
}

看起来很省事。然后：

Queue<String> q = new Queue<>();
q.enqueue("Muse");
q.enqueue("Pearl Jam");
q.clear();                  // ← 来自基类的方法，Queue 完全不知情
q.enqueue("Nirvana");
q.dequeue();                  // IndexOutOfBoundsException

作者补了一刀：抽象基类无法用 mock 替换。他点名 Apache CXF 有四五层继承的类，"隔离问题非常困难"。同一句批评今天适用于任何要求你 extends SomeFrameworkBase 的框架。

10.4正解：程序化配置

解药出奇地简单：把插件当作框架的一个依赖来对待，让使用者自己负责创建它。作者用 JSR-303（Bean Validation）作为范例。

第一步，用元注解代替字符串来指定插件类：

@Target(ElementType.FIELD)
@Retention(RetentionPolicy.RUNTIME)
@ConstraintValidator(LengthConstraint.class)     // 类型安全！拼错 = 编译错误
public @interface Length {
    int min();
    int max();
}

这一步同时解决了三个问题：拼错类名（编译错误）、拼错属性名（编译错误）、插错类型（@ConstraintValidator 只接受 Constraint 的子类型）。

第二步，也是关键的一步——把"怎么创建插件"这件事交出去：

public interface ConstraintFactory {
    <T extends Constraint> T getInstance(Class<T> constraintClass);
}
public class GuiceConstraintFactory implements ConstraintFactory {
    private final Injector injector = Guice.createInjector(new MyModule());

    public <T extends Constraint> T getInstance(Class<T> key) {
        return injector.getInstance(key);      // 用我自己的注入器造
    }
}

于是插件可以正常地享受依赖注入：

public class LengthConstraint implements Constraint<Length> {
    private int min, max;
    private final StringTools tools;              // 注入的共享工具

    @Inject public LengthConstraint(StringTools tools) { this.tools = tools; }

    public void initialize(Length constraint) {     // 从注解读配置
        min = constraint.min();  max = constraint.max();
    }
    public boolean isValid(Object value) {
        if (value == null) return true;
        return tools.isLengthBetween(min, max, (String) value);
    }
}
写给框架作者的一句话

作者反复强调的判据只有一条：可测试性。它自然推导出松耦合、作用域、模块化设计。而框架最常犯的错，是"自己测得很严格，却完全没考虑使用者的代码好不好测"。

① 作者赌对了：JSR-303 的机制活到了今天

Bean Validation 早已进化到 Jakarta Validation 3.x（jakarta.validation），而那个关键接口原封不动地留了下来（改名 ConstraintValidatorFactory）。更妙的是：Spring 内置了它的实现，你什么都不用做——

public class OrderNumberValidator implements ConstraintValidator<OrderNumber, String> {
    private final OrderRepository repo;                // 直接注入 Spring bean
    OrderNumberValidator(OrderRepository repo) { this.repo = repo; }   // 构造器注入！

    public boolean isValid(String v, ConstraintValidatorContext ctx) {
        return repo.existsByNumber(v);
    }
}

幕后是 SpringConstraintValidatorFactory——就是作者手写的 GuiceConstraintFactory 的官方版本。这是全书预测最准的一节。

两个值得停下来看的细节
  • 把会话作用域注入请求作用域是安全的——宽的注入进窄的，没有越界风险（第 5 章那张时间线图的下半句）。反过来才危险。
  • newTweet 在字段初始化时就 new 好了。因为 HomePage 每个请求一个新实例，所以每个请求自然拿到一个干净的 Tweet，不可能被上个请求的数据污染。这是"用作用域代替手工状态管理"最典型的一笔。

@Immutable @Singleton

    private final Map<String, String> users;

        users.put("dhanji", "dirocks");
        this.users = Collections.unmodifiableMap(users);    // 冻结 → 真正不可变

    public boolean authenticate(String u, String p) {
        return users.containsKey(u) && users.get(u).equals(p);
    }
}

最值得注意的一个变化

B.1Butterfly Container：为 DI 定制的 DSL

由 Jakob Jenkov 贡献。它不是 XML，而是一门专门的小语言 BCS（Butterfly Container Script），语法刻意做成"属性文件 + Java 代码"的混合体：

myBean1 = * com.myapp.MyBean();
//  ①    ②③        ④        ⑤
  1. 工厂 ID —— 容器内唯一的键；
  2. 等号 —— 产品定义开始；
  3. 实例化模式 —— 就是作用域（见下表）；
  4. 工厂链 —— 描述怎么造出这个对象；
  5. 分号。
符号含义对应第 5 章
*每次调用新建无作用域 / prototype
1单例singleton
1T每线程一个线程作用域
1F享元：同参数返回同实例—（较少见）

工厂链是这门 DSL 最有意思的地方——它允许链式调用返回 void 的方法（DSL 自定义语法的自由度）：

myBean2 = * com.myapp.MyBean2("A Text", myBean1)
            .setMoreText("more text")
            .setAValue(1)
            .setMoreOfSomething("more...");

它还内建了第 3 章两个模式的原生支持：

上下文注入（Assisted）
myBean1 = * com.myapp.MyBean($0).setValue($1);
myBean2 = * myBean1(com.myapp.SomeBean(), "Value Text");
// $0 $1 就是运行时传入的上下文参数
重注入（Provider）
firstBean  = * com.myapp.FirstBean($0).setValue($1);
secondBean = * com.myapp.SecondBean()
                 .setFirstBeanFactory(#firstBean);
// # 前缀 = 注入工厂本身，而不是产品

更妙的一手：容器会把工厂适配到你自己的接口，从而不在你的代码里留下任何容器类型：

public interface FirstBeanFactory {
    FirstBean instance(long constructorParam, String value);   // 完全类型安全，零框架依赖
}
这个附录今天的价值

Butterfly Container 本身没有流行起来，但它演示的两件事都成了主流：① 注入"工厂"而不是"产品"（今天是 Provider / ObjectProvider / Supplier）；② 让容器实现你定义的工厂接口（今天是 Guice 的 FactoryModuleBuilder、Dagger 的 @AssistedFactory）。

作者自己也点出了 DSL 的代价：$0、$1 既没有名字也没有类型，"这会导致工厂定义里出现类型错误"——回到了第 2 章字符串键的老问题。这大概也是纯 DSL 路线最终没能胜出的原因：为 DI 造一门新语言，就得为它重建一整套类型检查和工具链。

B.2SmartyPants：Adobe Flex 上的 DI

由 Josh McDonald 贡献，为 Flex/Flash 应用做的 DI 框架，明确以 Guice 为蓝本。三个核心概念：

  • class + name 键 —— 就是第 2 章的组合键（类型必填，名字可选）；
  • 元数据请求注入 —— [Inject] / [Inject(name="mainWSDL")]；
  • ActionScript DSL 写规则：
injector.newRule().whenAskedFor(String).named("wsdl")
                  .useInstance("http://www.server.com/soap/service.wsdl");
injector.newRule().whenAskedFor(IServiceInterface).useSingletonOf(MyServiceImpl);

它还有一个 Java 侧没有的特性——live injection：

[Inject(name="userName", live)]
public var currentUsername:String;   // 源值变化时字段自动更新，类似数据绑定

Flash 平台已于 2020 年底停止支持，SmartyPants 自然随之消失。但"注入 + 响应式绑定"这个组合活了下来——今天在前端（React 的 Context + hooks、Angular 的 DI + signals）随处可见。

第 5 章

作用域：状态的容器

这是让注入器区别于服务定位器的那个特性。作用域是一个键所对应的实例保持同一的时间段。把状态的归属声明出来交给容器管理，业务代码就可以对"当前是谁的请求"这件事一无所知——而这正是它该有的样子。

  • no scope / prototype
  • singleton scope
  • 绑定的是键，不是类
  • 单例反模式
  • request / session
  • guice-servlet

5.1牙膏的比喻

作者用一家人刷牙来定义作用域，这个比喻好用到值得原样引进：

family.give("Joanie", injector.getInstance(Toothpaste.class));
family.give("Jackie", injector.getInstance(Toothpaste.class));
family.give("Sachin", injector.getInstance(Toothpaste.class));

代码一个字都不用改，但语义完全取决于 Toothpaste 被绑到什么作用域：

  • 单例作用域 = 全家共用一个浴室、一支牙膏。Sachin 最后刷，可能已经没牙膏了。
  • 无作用域 = 一人一个浴室、一支新牙膏。谁都不会被挤掉。

这就是作用域的全部价值：同样的调用，不同的状态语义，而调用方不知情。

它带来四个好处：让注入器管理对象的潜在状态；确保服务按需拿到新的依赖；按上下文隐式隔离状态；减少业务代码里"状态感知"的逻辑——这一条最重要，它让代码好测也好推理。

5.2无作用域：一次一个新的

作者在这里做了一个很细的辨析。无作用域不对应任何概念上的上下文：如果 Sachin 刷两次牙，就会造出四支牙膏，而"三个浴室"的模型里只该有三支。所以严格说，

精确定义

无作用域的含义是：注入器每次查找这个键，都构造并接线一个全新实例。没有任何上下文承诺。硬要说，它是一个"上下文完全绑定在引用者身上的、一瞬间的作用域"。

命名差异：Guice / PicoContainer 叫它默认作用域 / 无作用域；Spring 叫 prototype（键是"创建新对象的模板"）。

5.3单例作用域

单例的上下文就是注入器本身。一个注入器一个实例。注意这句话的限定语——

⚠ 最常见的误解

很多人以为单例意味着"整个应用一个实例"。在 DI 里不是。同一个应用里可以有多个注入器，每个注入器持有自己的一份单例。PicoContainer 干脆放弃了 singleton 这个词，改叫 cache scoping。

什么该是单例

  • 客户的汇聚点：数据库连接池——所有要连库的服务都要经过它。
  • 无状态服务：业务 API（PersonnelManager、SalaryManager）本身没有状态，只有不可变的数据访问依赖。此时单例比无作用域更优：可以启动时预建（省掉运行时构造开销）、调试时只有一个引用点、内存占用是常数而非线性。

什么不该只因为"贵"就设为单例——这一段作者写得很克制，值得抄下来：

别为了性能而单例

对象图大、依赖慢速外部资源、构造后要做昂贵计算——这些本身都不构成理由。该问的是上下文问题。数据库连接池设计上就该长期持有 → 单例合理。但一个 TCP socket，虽然建立昂贵，如果用户可能登出再登入到另一台服务器，那就是新的上下文，必须新实例。

"在没有看到明确的性能短板之前，别急着把对象优化成单例。这句话你可以在每次开始猜测和担心性能时对自己重复一遍。"

单例的试金石：这个对象是否应该和注入器活得一样久？

关键：绑定的是「键」，不是「类」或「对象」

5.4单例作用域 vs 单例「反模式」

这两个东西同名，但作者对后者态度极其激烈。先看反模式长什么样：

public class Console {
    private static Console instance = null;

    public static synchronized Console getInstance() {
        if (null == instance) instance = new Console();
        return instance;
    }
}

问题从测试开始暴露。有个类这样用它：

public class StockTicker {
    private Console console = Console.getInstance();   // 没有缝隙塞 mock
}

为了能测，你被迫给 Console 加一个 setInstance()。然后测试写成这样：

@Test public void printToConsole() {
    Console previous = Console.getInstance();
    try {
        Console.setInstance(new MockConsole());
        ...
    } finally {
        Console.setInstance(previous);      // 忘了就污染后面所有测试
    }
}

作者的评语："为了让测试跑起来而被迫增加代码或基础设施逻辑的模式，是好设计的糟糕仆人。"更糟的是——并行测试下这段代码完全失效，线程互相踩踏。这本该是一票否决。

5.5Web 作用域：请求与会话

单例和无作用域是"通用"作用域。还有一类作用域只在特定问题域里有意义——作者叫它们领域相关作用域。电影院里，每一场正在放映的电影是一个上下文；观众在这个上下文里存在。Web 应用则有两个几乎所有人都要用的领域作用域。

请求作用域怎么改变代码

作者用一个漫画书商店演示。最初 ComicSearch 什么都自己干：

public HTML searchForComics(String criteria, String username) {
    user.signIn(username);                                    // 认证逻辑
    List<Comic> suggestions = user.getItemsOfInterest();
    List<Comic> results = comicAccess.searchNoPriorPurchases(criteria, username);
    ...
}

把 UserContext 设为请求作用域、把登录动作移进一个 filter 之后：

@RequestScoped
public class ComicSearch {
    private final UserContext user;         // 容器保证这是「当前请求的」那个

    public HTML searchForComics(String criteria) {            // username 参数消失了
        List<Comic> suggestions = user.getItemsOfInterest();
        List<Comic> results = user.searchComics(criteria);
        ...
    }
}

业务方法回到了纯业务。认证逻辑只写一次，在 filter 里：

@Singleton
public class UserFilter implements Filter {
    private final Provider<UserContext> currentUser;    // 注意是 Provider！

    public void doFilter(ServletRequest req, ServletResponse res, FilterChain chain) {
        currentUser.get().signIn(...);
        chain.doFilter(req, res);
    }
}
⚠ 这里为什么必须用 Provider

UserFilter 是单例，UserContext 是请求作用域。如果直接注入 UserContext，单例会一直攥着第一个请求的那个实例不放——后面所有用户都会被当成第一个用户。这就是 scope-widening injection，第 6 章的主角。Provider 让每次 get() 都去问容器要"当前上下文的那一个"。

绑定写法

Guice + guice-servlet
bind(ComicAccess.class)
    .to(ComicAccessImpl.class)
    .in(Singleton.class);
bind(UserContext.class).in(SessionScoped.class);
bind(ComicSearch.class).in(RequestScoped.class);

// 或者直接注解在类上
@SessionScoped
public class UserContext { ... }

      class="ComicAccessImpl" scope="singleton"/>
<bean id="web.user"
      class="UserContext"  scope="session"/>
<bean id="web.comicSearch"
      class="ComicSearch"  scope="request"/>

会话作用域的价值：省掉重复工作

把 UserContext 从请求作用域升到会话作用域，立刻有两个收益：登录只需在会话开始时做一次，而不是每个请求做一次；而且可以安全地做备忘缓存：

public class UserContext {
    private List<Comic> itemsOfInterest;              // 备忘字段

    public List<Comic> getItemsOfInterest() {
        if (null == itemsOfInterest) { ... }          // 一个会话内只算一次
        return itemsOfInterest;
    }
}

每个用户有自己的备忘，互不干扰——因为它们在各自的会话作用域实例里。

⚠ 使用 Web 作用域的四条注意
  • 一个请求通常独占一个线程 → 请求作用域对象一般不需要线程安全，也一般不是线程安全的；
  • 但会话作用域不一样：同一个用户的多个并发请求会同时命中同一个会话实例；
  • 集成层通常把作用域实例缓存在 ThreadLocal 里 → 请求结束必须清理；
  • 少数情况下服务器会用多个线程服务一个请求（长轮询/异步），此时 ThreadLocal 的假设会崩。

最后一条在 2009 年是"少数情况"，今天是主流场景之一。见下方对照。

注意 Spring 的默认作用域是 singleton，Guice 的默认是 无作用域。这个差异从 2009 年一直保持到今天，是两个生态最容易互相踩坑的地方之一。

② 那个 Provider 技巧，Spring 做成了声明式

书里让 UserFilter 注入 Provider<UserContext>。Spring 提供了更省事的方案——作用域代理：

@Component
@SessionScope(proxyMode = ScopedProxyMode.TARGET_CLASS)     // 或直接用 @SessionScope，默认就带代理
public class UserContext { ... }

@Service                                    // 单例
public class ComicService {
    private final UserContext user;         // 注入的其实是一个代理
    ComicService(UserContext user) { this.user = user; }

    void search() { user.getItemsOfInterest(); }
    // ↑ 代理在每次方法调用时才去查「当前会话的真实实例」
}

代价是要用 CGLIB 生成子类 —— 于是第 8 章那些"代理拦不到 final/private 方法"的限制会原封不动地找上门。纯 ObjectProvider 写法没有这个副作用，在能选的时候更干净。

③ 最大的变化：请求作用域在响应式/异步里失效

原书那条"少数情况下服务器会用多个线程服务一个请求"的注脚，今天成了一整类架构：

  • Spring WebFlux / 响应式栈：没有 thread-per-request，一个请求会在多个线程上流转。@RequestScope 和 RequestContextHolder 基本不可用，取而代之的是把上下文放进 Reactor Context（contextWrite / deferContextual）——它沿着数据流传播，而不是沿着线程。
  • Kotlin 协程：用 CoroutineContext，同理。
  • 虚拟线程（Java 21+，Spring Boot 3.2 起可一键开启）：thread-per-request 模型回来了，所以 @RequestScope 又能用了。但 ThreadLocal 的成本模型变了——虚拟线程是百万级、朝生暮死的，为每个线程挂一份 ThreadLocal map 不再划算。

④ ScopedValue：为作用域而生的新语言特性

Java 25（2025-09 LTS）正式发布的 JEP 506 Scoped Values，几乎就是给这一章量身定做的：

private static final ScopedValue<UserContext> CURRENT_USER = ScopedValue.newInstance();

// 在 filter 里绑定，作用域的边界由代码块的词法结构决定
ScopedValue.where(CURRENT_USER, new UserContext(username))
           .run(() -> chain.doFilter(req, res));

// 下游任意深度读取，包括结构化并发派生出的子线程
UserContext user = CURRENT_USER.get();
ThreadLocal（书中的做法）ScopedValue
可变性可随时改写不可变
作用域边界靠你记得调 remove()由代码块决定，自动结束
忘记清理内存泄漏（线程池场景尤其严重）不可能发生
子线程继承InheritableThreadLocal，复制开销大结构化并发下天然可见，零复制
百万虚拟线程开销显著为此设计

第 6 章会手写一个基于 ThreadLocal 的事务作用域——那份代码在今天可以、也应该用 ScopedValue 重写。注意 JDK 团队明确说了不打算废弃 ThreadLocal，两者会长期共存。

⑤ 单例反模式：结论没变，但有了新的犯法姿势

手写 getInstance() 今天很少见了。但等价物层出不穷：Kotlin 的 object 单例、Java 的静态工具类持有状态、以及最常见的——把 Spring 容器塞进静态字段（ApplicationContextHolder.getBean(...)）。作者对 Console.getInstance() 的全部批评，逐字适用于后者。

⑥ Spring 侧的作用域配置

原书要在 web.xml 里注册 RequestContextListener。Spring Boot 把这一步自动化了，你只要加注解就行。guice-servlet 也还在，但 Guice 7 起用的是 jakarta.servlet。

第 11 章

实战：Crosstalk

最后一章把前十章串起来：一个微博客（Twitter 克隆）的完整实现。它足够小，能在几页纸里讲完；又足够真，涵盖了表现层、持久层、安全层、模块边界、作用域、拦截、生命周期——每一样都能在前面的章节里找到出处。

  • Guice + Hibernate + Sitebricks
  • 三层包结构
  • request / session 作用域
  • 安全拦截器
  • PersistenceFilter 生命周期

11.1需求与技术选型

需求极简：用户登录后，在自己的主页上发短消息（tweet）。由此推出三件事——认证用户、保护主页、把 tweet 存进数据库；外加一个非功能要求：并发。

11.2组装：一个类说清全部接线

public final class CrosstalkBootstrap extends GuiceServletContextListener {
    @Override protected Injector getInjector() {

        Module services = new ServicesModule();                    // ① 数据 + 安全

        Module sitebricks = new SitebricksModule() {               // ② 页面路由
            protected void configureSitebricks() {
                at("/home").show(HomePage.class);
                at("/login").show(LoginPage.class);
            }
        };

        Module servlets = new ServletModule() {                    // ③ 请求管线
            protected void configureServlets() {
                filter("/*").through(PersistenceFilter.class);     // 必须在 sitebricks 之前
                install(sitebricks);
            }
        };

        return Guice.createInjector(services, servlets);
    }
}

这个类就是第 1 章说的"应用启动器"——它调用注入器，而它自己不参与任何业务行为。整个应用只有这一处调用了容器。

web.xml 里只剩两件事：把所有请求交给 GuiceFilter，以及注册这个启动器。

11.3包结构：只暴露接口

包内容可见性

…crosstalk.servicesTweetManager、UserManager、AuthenticationManager 是接口；
HibernateTweetManager、InMemoryUserManager、SecurityInterceptor 全是包级私有		只暴露接口 + ServicesModule
…crosstalk.tweetsTweet（领域模型）public（Hibernate 要映射）

这正是第 9 章"只把接口、枚举、注解、抽象类设为 public"的落地。想把持久化从 Hibernate 换成别的？只动 services 包内部，表现层一行不改。

11.4表现层：作用域的实战

@At("/home") @Select("action") @RequestScoped
public class HomePage {
    private final TweetManager tweetManager;    // 单例服务
    private final User user;                    // 会话作用域

    private List<Tweet> tweets;                 // 页面状态：本次请求专属
    private Tweet newTweet = new Tweet();       // 每次请求一个全新的空 tweet

    @Inject public HomePage(TweetManager tweetManager, User user) { ... }

    @Get public String get() {
        this.tweets = tweetManager.tweetsFor(user.getUsername());
        return null;                            // null = 留在当前页
    }

    @Post public String post() {
        newTweet.setAuthor(user.getUsername());
        tweetManager.addTweet(newTweet);
        return "/home";                         // 重定向，避免重复提交
    }

    @Get("logout") public String logout() {
        user.logout();
        return "/login?message=Bye.";
    }
}
两个值得停下来看的细节
  • 把会话作用域注入请求作用域是安全的——宽的注入进窄的，没有越界风险（第 5 章那张时间线图的下半句）。反过来才危险。
  • newTweet 在字段初始化时就 new 好了。因为 HomePage 每个请求一个新实例，所以每个请求自然拿到一个干净的 Tweet，不可能被上个请求的数据污染。这是"用作用域代替手工状态管理"最典型的一笔。

User 就是第 5 章那个 UserContext 的实战版：

@SessionScoped @NotThreadSafe
public class User {
    private String username;
    public String getUsername()          { return username; }
    public void login(String username)   { this.username = username; }
    public void logout()                 { this.username = null; }
}

整个应用里再没有任何一处读写 HttpSession——"当前是谁"这件事被完全隐藏在作用域后面。

11.5持久层

@Immutable @Singleton
class HibernateTweetManager implements TweetManager {     // 注意：包级私有
    private final Provider<Session> session;              // ← 不是 Session

    @Inject HibernateTweetManager(Provider<Session> session) { this.session = session; }

    @Finder(query = "from Tweet where author = :author")   // 方法体是空的，被拦截替换
    public List<Tweet> tweetsFor(@Named("author") String author) {
        return Collections.emptyList();
    }

    public void addTweet(Tweet tweet) { session.get().save(tweet); }
}

三个模式同时出现在这十行里：Provider 防作用域越界（第 3、6 章）、不可变单例（第 9 章）、方法装饰（第 3 章的 AOP 注入——@Finder 让一个空方法变成查询）。

用户管理则用了一个硬编码的实现，但仍然演示了正确姿势：

@Immutable @Singleton
class InMemoryUserManager implements UserManager {
    private final Map<String, String> users;

    InMemoryUserManager() {
        Map<String, String> users = new HashMap<>();
        users.put("dhanji", "dirocks");
        this.users = Collections.unmodifiableMap(users);    // 冻结 → 真正不可变
    }
    public boolean authenticate(String u, String p) {
        return users.containsKey(u) && users.get(u).equals(p);
    }
}

注意这里做对了第 9 章谜题 4 的功课：局部变量构造完毕后立即冻结，没有任何外部引用能改它。

11.6安全层与生命周期

bindInterceptor(
        not(subclassesOf(LoginPage.class)),                          // 除了登录页
        annotatedWith(Get.class).or(annotatedWith(Post.class)),       // 所有事件方法
        new SecurityInterceptor(manager));
class SecurityInterceptor implements MethodInterceptor {
    public Object invoke(MethodInvocation mi) throws Throwable {
        if (authenticationManager.isLoggedIn()) return mi.proceed();
        return "/login";                        // 未登录 → 直接重定向，目标方法不执行
    }
}

第 8 章说的"拦截器能阻止调用"，这就是最典型的用法。安全策略集中在一处声明，页面类里一行安全代码都没有。

生命周期方面，PersistenceFilter 一个组件挑了两副担子：

  • init()：建连接池、建表、启动 HSQLDB；destroy()：关闭 Hibernate SessionFactory——与 Web 应用的生命周期对齐（第 7 章）；
  • 每个请求：开启和关闭一个 Hibernate 工作单元——这就是第 5、6 章的请求作用域。

整个应用的现代版本大概长这样：

@Entity
class Tweet {
    @Id @GeneratedValue Long id;
    String author;
    String text;
    Instant createdOn = Instant.now();
}

interface TweetRepository extends JpaRepository<Tweet, Long> {
    List<Tweet> findByAuthorOrderByCreatedOnDesc(String author);   // 无需写查询
}

@Controller
class HomeController {                                  // 单例，不是请求作用域
    private final TweetRepository tweets;               // 构造器注入，final
    HomeController(TweetRepository tweets) { this.tweets = tweets; }

    @GetMapping("/home")
    String home(@AuthenticationPrincipal UserDetails user, Model model) {
        model.addAttribute("tweets", tweets.findByAuthorOrderByCreatedOnDesc(user.getUsername()));
        return "home";
    }

    @PostMapping("/home")
    @Transactional
    String post(@AuthenticationPrincipal UserDetails user, @RequestParam String text) {
        tweets.save(new Tweet(user.getUsername(), text));
        return "redirect:/home";
    }
}
最值得注意的一个变化

现代版的控制器是单例，不是请求作用域。"当前用户"通过方法参数（@AuthenticationPrincipal）传进来，而不是通过一个会话作用域的字段。

这是一次真实的观念迁移：用无状态 + 显式传参，代替有状态 + 作用域。原因正是第 5、6 两章列的那些代价——作用域越界、线程安全、内存泄漏、测不出来。今天的默认答案是：能不用作用域就不用；请求相关的数据用参数传，别放进字段。

作者关于作用域的全部技术论述依然正确，只是行业在"什么时候该用它"这个问题上变保守了——和第 6 章"自定义作用域"的结论一致。

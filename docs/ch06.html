第 6 章

自定义作用域与陷阱

上一章讲了容器给你的作用域，这一章你自己造一个——以及为此付出的代价。作用域是全书威力最大也最危险的特性：它把状态管理反转给了容器，而当两个不同寿命的对象被接在一起时，事故会以内存泄漏、线程可见性错乱、静默的错误结果这三种面目出现，且单元测试一个都抓不到。

  • 自定义作用域三问
  • 事务作用域
  • Scope 接口
  • scope-widening
  • out-of-scope 对象
  • 内存泄漏
  • 缓存 / 网格作用域

6.1动手造一个事务作用域

动手之前先回答三个问题。作者把它们放在最前面，是有道理的——第二个问题几乎是所有自定义作用域事故的根源：

  1. 这个作用域代表的上下文是否定义清晰？（起点在哪、终点在哪）
  2. 对象必须活满整个作用域——对该作用域里的每一个键都成立吗？绝不能在一个作用域里出现两种寿命。
  3. 会不会有多个线程访问这个作用域里的对象？

事务（ACID：原子、一致、隔离、持久）恰好三条全过：起止明确（begin/commit），寿命一致，且通常限定在单线程内。

为什么需要它：核电站的例子

public class PowerStation {
    public void start() {
        transaction.begin();
        boolean failed = false;
        try {
            chamber1.fire();  chamber2.fire();  chamber3.fire();
        } catch (StartFailedException e) {
            failed = true;
        } finally {
            if (failed) transaction.rollback(); else transaction.commit();
        }
    }
}
public class Chamber {
    private final Gauge gauge;
    public void fire() {
        gauge.measure();
        if (gauge.temperature() > 100) throw new StartFailedException();
    }
}

需求是三个燃烧室的温度之和不能超过 100。现在 Gauge 是无作用域的，每个 Chamber 各有一个仪表，量的是各自的温度——需求实现不了。

那设成单例？也不对——那样连备用燃烧室、连根本不是燃烧室的组件都会共享这个仪表。正确的上下文是"这一次启动"，也就是这个事务。于是：

@TransactionScoped
public class Gauge { ... }

PowerStation、Chamber 和它们的方法一行都不用改。这就是作用域的威力：换一个词，语义全变，业务代码毫不知情。

Scope 接口只有一个方法

public interface Scope {
    <T> Provider<T> scope(Key<T> key, Provider<T> unscoped);
}

两个参数的含义是理解自定义作用域的钥匙：key 是要被作用域化的键；unscoped 是一个"无作用域的 provider"——当上下文里还没有这个实例时，用它造一个新的。

Guice 实现

public class TransactionScope implements Scope {
    private final ThreadLocal<Map<Key<?>, Object>> instances = new ThreadLocal<>();

    public <T> Provider<T> scope(final Key<T> key, final Provider<T> unscoped) {
        return new Provider<T>() {
            public T get() {
                Map<Key<?>, Object> map = instances.get();
                if (null == map)
                    throw new OutOfScopeException("no transaction was active");
                if (!map.containsKey(key)) map.put(key, unscoped.get());
                return (T) map.get(key);
            }
        };
    }

    public void beginScope() { instances.set(new HashMap<>()); }
    public void endScope()   { instances.remove(); }
}

那个加粗的检查非常重要。在事务之外请求事务作用域的对象，说明程序逻辑或配置有错。如果不检查，你会得到一个空指针或者更糟的静默错误，然后花几小时在错误的地方找 bug。

注册：

bindScope(TransactionScoped.class, new TransactionScope());

@Retention(RetentionPolicy.RUNTIME)
@ScopeAnnotation                       // 元注解：告诉容器这是个作用域注解
public @interface TransactionScoped { }

Spring 实现

接口多三个方法，但核心的 get() 和 Guice 的 scope() 语义一致：

public interface Scope {
    Object get(String key, ObjectFactory unscopedProvider);  // 等价于 Guice 的 scope()+get()
    Object remove(String key);                               // 从当前上下文剔除一个键
    String getConversationId();                              // 当前上下文的唯一标识
    void registerDestructionCallback(String key, Runnable cb); // 出作用域时的清理钩子（第 7 章）
}
<bean class="org.springframework.beans.factory.config.CustomScopeConfigurer">
    <property name="scopes"><map>
        <entry key="transaction"><bean class="my.custom.TransactionScope"/></entry>
    </map></property>
</bean>

<bean id="gauge" class="nuclear.Gauge" scope="transaction"/>

6.2陷阱一：单例必须线程安全

⚠ 没有例外

"Singletons absolutely must be thread-safe — no exceptions."

两条路。首选不可变：

@Immutable @Singleton
public class MySafeObject {
    private final Dependency dep1;
    private final Dependency dep2;
    @Inject public MySafeObject(Dependency d1, Dependency d2) { ... }
    // 没有 setter，没有能改变依赖状态的方法
}

做不到不可变时（比如为了破循环引用而用了 setter），退而求其次用 volatile：

安全
@ThreadSafe @Singleton
public class MySafeObject2 {
    private volatile Dependency dep1;
    private volatile Dependency dep2;

    @Inject public void set(Dependency d1, Dependency d2) {
        this.dep1 = d1; this.dep2 = d2;
    }
}
致命
@NotThreadSafe @Singleton
public class MyUnsafeObject {
    private Dependency dep1;      // 非 final 非 volatile
    private Dependency dep2;

    @Inject public void set(Dependency d1, Dependency d2) {
        this.dep1 = d1; this.dep2 = d2;
    }
}

右边为什么致命：Java 语言对非 final、非 volatile 字段在线程间的可见性不做任何保证。设置它的那个线程能看到值，别的线程可能永远看不到。JVM 允许每个线程持有本地缓存副本。第 9 章会详细展开。

作者对线程安全的态度值得抄下来："不存在能判定一个类完全线程安全的试金石。仔细推理它的线程环境；探索常见和非典型的使用场景；试着说服至少一个别人；主动寻找缺陷，永远不要假设它们不存在；验证你的每一个假设。测试，测试，再测试。"

6.3陷阱二：作用域越界注入（scope-widening）

本章的核心。把窄作用域的对象注入进宽作用域的对象，被注入的那个就脱离了自己作用域的管辖——上下文结束了，它还活着。

作者特别提醒：越界不限于"窄 vs 宽"，同一个作用域的两个不同上下文之间也算（比如两个用户会话被一个单例桥接起来）。

事故 A：静默的错误结果

@Singleton
public class TextReader {
    private final WordCounter counter;     // WordCounter 是无作用域的

    public void scan(List<String> strings) {
        for (String s : strings) counter.count(s);
        System.out.println("Total words: " + counter.words());
    }
}

每次调用都传 7 个词，期望每次都打印 7。实际输出：

Total words: 7
Total words: 14
Total words: 21

两种修法：

  • 降低宽的那个的作用域——把 TextReader 也改成无作用域。最简单，但不总是可行。
  • 注入 Provider——第 3 章的重注入模式，本质上 scope-widening 就是重注入问题的一种形态。
⚠ 用了 Provider 也可能出错 
public void scan(List<String> strings) {
    for (String s : strings) counterProvider.get().count(s);       // 每个词一个新计数器
    System.out.println("Total: " + counterProvider.get().words()); // 又一个新的 → 永远打印 0
}

正确写法是每个方法调用取一次：WordCounter counter = counterProvider.get(); 然后复用它。作者说得很实在：这种错误"多半会让你满世界找 bug，就是不会想到作用域上"。

事故 B：out-of-scope 对象

把 servlet 标成请求作用域：

@RequestScoped
public class HelloServlet extends HttpServlet {
    public void init(ServletConfig config) { ... }    // 容器启动时调用
}

Web 应用启动时 init() 被触发，此时没有任何活动请求 → OutOfScopeException → 整个应用起不来。会话作用域同理。

解法是第 3 章的 Adapter：用一个单例包住它，把"生命周期方法"留在单例里，把"请求内的方法"委托下去：

@Singleton
public class HelloServletAdapter extends HttpServlet {
    private final Provider<HelloServlet> delegate;

    public void init(ServletConfig config) { /* 初始化逻辑留在这一层 */ }

    public void service(HttpServletRequest req, HttpServletResponse res) {
        delegate.get().service(req, res);    // 这里一定在请求内，安全
    }
}

事故 C：线程安全

单例的窄作用域依赖，会被单例的所有调用线程碰到。

@Singleton
public class TextPrinter {
    private final Counter counter;                // @NotThreadSafe

    public void print(String text) {
        System.out.println(text);
        counter.increment();
        if (counter.getCount() == 100) System.out.println("done!");
    }
}

问题分两层。第一层是可见性：count 非 volatile，各线程看到的值不一致。加了 volatile 之后还有第二层——两个线程可能一个把计数推到 100、另一个推到 101，然后两个都跳过了 == 100 的判断，"done!" 永远不打印。

解法是互斥：

@ThreadSafe @Singleton
public class TextPrinter {
    public synchronized void print(String text) { ... }   // 由持有者负责加锁
}

注意 Counter 本身仍然标注 @NotThreadSafe——因为它作为一个组件依然可以被不安全地使用。责任在持有它的单例身上。

事故 D：内存泄漏

@Singleton
public class BadServlet extends HttpServlet {
    public final List<WebPage> pages = new ArrayList<>();     // 单例持有，永不释放

    public void service(HttpServletRequest req, HttpServletResponse res) {
        pages.add(page.get());                              // 每个请求攒一个
        pages.get(0).handle(req, res);
    }
}

单例活到应用关闭，所以它引用的一切都活到应用关闭。不停刷新这个 URL，最终 OutOfMemoryError。改法很简单——用完就丢：

public void service(HttpServletRequest req, HttpServletResponse res) {
    page.get().handle(req, res);     // 不保存引用，GC 可以回收
}
⚠ 四类事故的共同点

它们全都测不出来。单元测试测不出（每个类都是对的），集成测试也不可靠（并发和内存问题需要特定负载才显形）。作者给出的唯一防线是设计纪律：

  • 让整个对象图绑在最窄的作用域上；
  • 必须跨作用域时，用 Provider 或 Adapter；
  • 想清楚并说服另一个人；
  • 能避免就彻底避免。

6.4把作用域用出花来

最后一节是前瞻性的，2009 年只能算构想，今天已经全部落地：

  • 缓存作用域：实例透明地从缓存（甚至磁盘缓存）中获取，可以跨越注入器的多次生命周期。作者举的例子是游戏存档。
  • 网格作用域：实例活在一个跨机器的分布式缓存里（书里点名 Oracle Coherence）。一台机器上注入的对象，整个集群都能拿到。作者说最简单的用例是把用户凭证复制到整个集群，从而实现单点登录。
  • 透明网格计算：把一次方法调用编排到多台机器上（书里对比了 Apache Hadoop 的 MapReduce）。作者当时的判断是"已有的努力都集中在任务切分与分发上，缺的是面向客户端的架构模式"。
2026 对照

① 手写 ThreadLocal 作用域：换成 ScopedValue

6.1 节那份 TransactionScope 的核心是 ThreadLocal<Map> + 手动 begin/end。它有两个已知弱点：忘了 endScope() 就在线程池里泄漏；子线程看不到上下文。Java 25 的 ScopedValue（JEP 506）两个都解决了：

// 上下文的边界由代码块决定，不可能忘记关
static final ScopedValue<Map<Key<?>, Object>> TXN = ScopedValue.newInstance();

ScopedValue.where(TXN, new HashMap<>()).run(() -> {
    txn.begin();
    try { chamber1.fire(); chamber2.fire(); chamber3.fire(); txn.commit(); }
    catch (StartFailedException e) { txn.rollback(); }
});   // ← 出了这个块，上下文自动消失，没有 remove() 可以忘

作用域实现里的 if (null == map) throw new OutOfScopeException(...) 依然要写——只是改成检查 TXN.isBound()。作者当年为"作用域外访问"设的那道防线，今天一个字都不用改。

② 事务作用域本身：早就不用自己写了

核电站那个例子在 2009 年需要自定义作用域，因为当时的 @Transactional 生态还不完善。今天：

@Service
class PowerStation {
    @Transactional                          // Spring / Jakarta 都有
    public void start() {
        chamber1.fire(); chamber2.fire(); chamber3.fire();
        // 抛异常 = 自动回滚，不用写 try/finally
    }
}

而"三个燃烧室共享一个仪表"这类需求，今天的标准解法是把 Gauge 当参数显式传下去，或者用 TransactionSynchronizationManager.getResource() 这种官方的事务级资源绑定——不再鼓励为它造一个新的作用域。原因见下一条。

③ 自定义作用域的行业态度：变保守了

作者当年鼓励"按你的问题域设计作用域"。十七年过去，业界的共识明显收紧：

  • Spring 的自定义 Scope 接口一直都在，但生产项目里罕见；
  • Guice 官方 wiki 现在直接建议："custom scopes are rarely needed"，优先考虑显式传参；
  • 原因正是 6.3 节列的四类事故——自定义作用域的收益是省几行代码，代价是引入一整类测不出来的 bug。这个交易在大多数项目里不划算。

换句话说：这一章最有价值的部分不是 6.1（怎么造），而是 6.3（为什么最好别造）。

④ Scope-widening：容器开始帮你挡了

手段做什么
Spring 作用域代理
ScopedProxyMode.TARGET_CLASS		注入的是代理，每次方法调用时才解析真实实例 → 从机制上杜绝了单例攥住请求对象
Spring ObjectProvider书里 Provider 的加强版，还能 getIfAvailable()
Guice 内建检查把 @RequestScoped 注入 @Singleton 时，运行时抛 OutOfScopeException（书里的场景）
Simple Injector（.NET）直接把这类问题命名为 Captive Dependency，并在 container.Verify() 时启动期报错——这是目前最彻底的方案

Java 侧至今没有等价的启动期全图校验，所以本章的纪律依然要靠人。

⑤ 内存泄漏：工具追上来了

BadServlet 那类泄漏今天用 JFR（Java Flight Recorder）+ 堆转储分析能在几分钟内定位到"谁持有了这个引用"。生产环境有 -XX:+HeapDumpOnOutOfMemoryError 兜底。但注意：工具只能事后诊断，防不住。

⑥ 缓存 / 网格作用域：全部成真了

2009 年的构想2026 年的现成方案
缓存作用域Spring Cache 抽象（@Cacheable）+ Caffeine / Redis
网格作用域 · 会话复制Spring Session（Redis / Hazelcast / JDBC 后端）—— 几乎精确实现了作者说的"跨集群共享会话作用域实例"
单点登录OIDC / OAuth2 + 无状态 JWT，或 Spring Session 共享；方向变了：主流做法是不要有服务端会话状态
透明网格计算Hadoop → Spark / Flink；"面向客户端的架构模式"这个空白，最终由 gRPC / 服务网格 / Actor 模型填上，而不是由 DI 容器填上

最后一条值得注意：作者希望 DI 容器把远程调用做成透明的注入。历史给的答案是否——分布式的失败模式（网络分区、超时、部分失败）不该被透明地隐藏起来。这是"透明远程调用"这个想法在业界的第二次失败（第一次是 EJB Remote / CORBA）。

⑦ 线程安全注解

书里用的 @Immutable / @ThreadSafe / @GuardedBy 来自 Java Concurrency in Practice（jcip-annotations，仓库里就有这个 jar）。它们今天基本没人用了——但这个习惯本身值得保留，只是换成了：Error Prone 的 @Immutable（编译期强制检查，不只是文档）、JSpecify 的空安全注解（Spring 7 全面采用）、以及最好的一招——用 record 让不可变成为类型的性质而不是注释。

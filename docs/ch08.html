第 8 章

拦截、代理与 AOP

第 7 章讲的是把事件往下通知给对象；这一章相反——改变对象对调用者的反应。事务、安全、日志这类散落在几百个方法里的重复代码，可以收进一处，用匹配器批量织入。代价是：你从此活在动态代理的规则之下，而这些规则有五条硬边界。

  • 织入 weaving
  • 切点 / 匹配器
  • JDK Proxy · CGLib
  • 拦截顺序
  • 声明式事务
  • 方法级安全
  • 代理的五条边界

8.1问题：横切关注点

手写事务
public class Brokerage {
    private final TransactionManager txn;

    public void placeOrder(Order order) {
        txn.beginTransaction();
        try {
            ...
        } catch (DataException e) {
            txn.rollback();
        } finally {
            if (!txn.rolledBack()) txn.commit();
        }
    }
}
声明式
public class Brokerage {

    @Transactional
    public void placeOrder(Order order) {
        ...
    }
}
// 少了：try/catch/finally、
//       对 TransactionManager 的依赖、
//       每个业务方法的重复副本

右边发生的事情叫织入（weaving），被插入的行为叫通知（advice）。织入有三个时机：

Guice 的拦截器

public class TracingInterceptor implements MethodInterceptor {   // AopAlliance 接口
    public Object invoke(MethodInvocation mi) throws Throwable {
        System.out.println("enter " + mi.getMethod().getName());
        try {
            return mi.proceed();               // 放行到真实方法
        } finally {
            System.out.println("exit " + mi.getMethod().getName());
        }
    }
}
bindInterceptor(any(), any(), new TracingInterceptor());
//              ↑类匹配器  ↑方法匹配器

注意 finally：异常也要保证出口日志被打印。这是拦截器的基本纪律。

Spring 的切面

<aop:config>
    <aop:aspect ref="tracer">
        <aop:pointcut id="pointcuts.anyMethod"
                      expression="execution(* example.*.*(..))" />
        <aop:around pointcut-ref="pointcuts.anyMethod" method="trace"/>
    </aop:aspect>
</aop:config>

AspectJ 的切点表达式是一门专门的匹配语言，比 Guice 的 Matcher 表达力强得多，代价是它是字符串（回到第 2 章的字符串键问题：拼错了运行时才知道）。

代理到底是什么

理解代理最好的方式，是想象你手写了这个子类：

public class ChefProxy extends Chef {              // 就是个子类
    private final MethodInterceptor interceptor;
    private final Chef chef;

    public void cook()  { interceptor.invoke(new MethodInvocation() { ... }); }
    public void clean() { interceptor.invoke(new MethodInvocation() { ... }); }
    // 每个方法都不干活，只是转交给拦截器；由拦截器决定要不要 proceed()
}

代理库做的事就是在运行时生成这段字节码。两种工具：

JDK java.lang.reflect.ProxyCGLib
能代理什么只能是接口具体类（生成子类）
需要ClassLoader + 接口数组 + InvocationHandler目标类 + MethodInterceptor
放行method.invoke(target, args)methodProxy.invokeSuper(proxy, args)
作者的建议能用接口代理就用接口代理，除非你确信需要类代理并理解其后果

过多的通知很危险

作者用一个极简的例子说明顺序问题。模板输出 Hello, Bob!，两个拦截器分别加粗和包 HTML：

顺序错了
bindInterceptor(..., new BoldDecoratingInterceptor());
bindInterceptor(..., new HtmlDecoratingInterceptor());

// 输出：
<b><html><body>Hello, Bob!</body></html></b>
顺序对了
bindInterceptor(..., new HtmlDecoratingInterceptor());
bindInterceptor(..., new BoldDecoratingInterceptor());

// 输出：
<html><body><b>Hello, Bob!</b></body></html>
⚠ 单元测试抓不到这个

两个拦截器各自的单元测试都会通过，被拦截类的单元测试也会通过（测试时根本没有拦截器）。这个 bug 只存在于"组合"里。——和第 6 章 scope-widening 是同一类问题。

作者给的防线是 8.3 节末尾的纵向集成测试：把预期的拦截器组合装起来，走一遍真实调用路径。

8.2两个真实用例

声明式事务

没有拦截时，每个方法都要写这一坨：

public void newCar(Car car) {
    EntityTransaction txn = em.getTransaction();
    txn.begin();
    boolean succeed = true;
    try { em.persist(car); }
    catch (RuntimeException e) { txn.rollback(); succeed = false; }
    finally { if (succeed) txn.commit(); }
}

加上 @Transactional 后剩下：

@Transactional
public void newCar(Car car) { em.persist(car); }

作者特意点出一个容易被忽略的收益：上面那段手写代码把异常吞掉了（catch 之后什么都没做）。声明式事务除了省样板，还把"什么异常该回滚"变成了框架统一的、正确的语义。

方法级安全

<security:global-method-security>
    <security:protect-pointcut
        expression="execution(* example.PhoneService.*(..))"
        access="ROLE_ADMIN" />
</security:global-method-security>

拦截器在方法执行前校验当前用户的角色，不够就抛异常——目标方法根本不会执行。这是拦截器相对于"在方法开头写一行检查"的关键优势：它能阻止调用，而且这个策略是集中声明的。

8.3代理的五条边界

本章最有价值的一节。记住一句话就够了：代理只是一个子类。凡是子类不能覆盖的东西，代理都拦不到。

边界 1：相同性判断不可靠

final Painting picasso = new Painting("Picasso");
Injector injector = Guice.createInjector(... bind(Painting.class).toInstance(picasso) ...);

assert picasso == injector.getInstance(Painting.class);   // 失败！拿到的是代理

两个常见的连带错误：

会拿到代理的类名
public class ANoisyService {
    public final Logger log =
        Logger.getLogger(getClass().getName());
    // 可能打印成 ANoisyService$$EnhancerByCGLIB$$…
}
显式写死类字面量
public class ANoisyService {
    public final Logger log =
        Logger.getLogger(ANoisyService.class.getName());
}
把代理排除在相等之外
public boolean equals(Object o) {
    if (o == null ||
        o.getClass() != EqualToNone.class) return false;
    ...
}
用 instanceof
public boolean equals(Object o) {
    if (!(o instanceof EqualToNone)) return false;
    ...
}

边界 2：静态方法

Java 的静态方法不能被覆盖，只能被隐藏。作者做了一个很好的实验：子类定义同名 static 方法，从子类里调用会用子类版本，看起来像"覆盖"——但那只是词法作用域的效果。从外部调用必须显式指明是哪一个。结论：需要动态行为的逻辑，不要放在静态方法里。

边界 3：私有方法

把 clean() 改成 private，拦截器就完全看不到它了。解法是提升可见性：

可见性能被代理？说明
private✗子类不可见
包级（无修饰符）✓推荐：包外完全不可见，但代理通常生成在同包下
protected✓对同层级以外隐藏，但其他模块的子类仍能看到
public✓全开放

边界 4：final 方法与 final 类

final 不是可见性修饰符，但它同样阻止覆盖。类是 final 时连子类都生成不了。解法是委托：

class FrenchChefDelegator implements Chef {
    private final FrenchChef delegate;                // 组合而非继承
    public void cook()  { delegate.cook(); }
    public void clean() { delegate.clean(); }
}

作者的建议：拿不准就用组合，别用继承；更好的做法是直接代理接口。

边界 5：字段

AspectJ 的构建期织入能改字段，Spring AOP 和 Guice AOP 都不能。而且——

public class FrenchChef implements Chef {
    private final RecipeBook recipes = new RecipeBook();   // 手工构造
    public void cook() { recipes.read("ratatouille"); }
}

拦截器永远够不到 RecipeBook 的方法，因为它不是容器创建的。这句话反过来说更重要：任何你希望被拦截的依赖，都必须由注入器创建。手工 new 出来的对象自动退出 AOP 体系——这是第 1 章"别自己 new"的又一条理由。

拦截与测试

拦截让"单元行为"和"语义行为"分了家：TicketBooth.purchase() 的单元测试只知道它卖票；加了一个"每 100 位顾客打折"的拦截器后，系统的实际语义变了。作者的解法是纵向集成测试：

@Test public void discountEveryHundredthTicket() {
    Injector injector = Guice.createInjector(new AbstractModule() {
        protected void configure() {
            bind(TicketBooth.class);
            bindInterceptor(any(), any(), new DiscountingInterceptor());   // 装上真实拦截器
        }
    });
    TicketBooth booth = injector.getInstance(TicketBooth.class);
    for (int i = 1; i < 101; i++) {
        Ticket t = booth.purchase(Money.inDollars("200"));   // 走真实调用路径
        if (i == 100) assert t instanceof DiscountedTicket;
    }
}

"当程序里有依赖这类副作用的服务时，纵向集成测试提供的信心远大于各个单元测试之和。"

2026 对照

① 五条边界：全部成立，而且多了一条最常见的

自调用（self-invocation）——书里完全没提，但它是今天 Spring 用户踩得最多的坑：

@Service
public class OrderService {
    public void placeOrders(List<Order> orders) {
        for (Order o : orders) this.save(o);      // ← this 是真实对象，不是代理！
    }

    @Transactional
    public void save(Order o) { ... }               // 事务静默失效，一行报错都没有
}

原因完全在书的框架内：调用链是 代理.placeOrders() → 真实对象.placeOrders() → 真实对象.save()，第二跳之后代理就不在链上了。三种解法：把 save 挪到另一个 bean（首选，通常也说明职责该分开）；自注入 ObjectProvider<OrderService>；或改用 AspectJ 编译期织入。

② 代理技术栈换代

20092026
独立的 cglib.jarSpring 内嵌了重打包的 CGLIB（org.springframework.cglib），你不用自己引
AopAlliance 独立 jar同样被重打包进 spring-aop；Guice 仍用它
CGLIB 生成子类ByteBuddy 成了生态主流（Mockito、Hibernate 都用它）
—Spring Boot 2.0 起 proxyTargetClass=true 是默认值 → 默认走 CGLIB 类代理，而不是 JDK 接口代理
—Java 17+ 的强封装让"深度反射"受限，跨模块代理需要 --add-opens

注意最后两条的组合效果：默认走类代理，意味着"边界 3/4"（private、final）比 2009 年更容易被撞上。

③ 语言演化制造的新摩擦

  • Kotlin 的类和方法默认是 final → 直接触发边界 4。解法是 kotlin-spring 编译器插件（allopen），它自动给 Spring 注解标注的类"解 final"。
  • record 是隐式 final 的 → 无法被类代理。这其实是好事：record 是数据，本来就不该被 AOP 拦截（呼应第 9 章"数据对象 vs 服务对象"）。
  • 虚拟线程：拦截器里如果持有锁或用 ThreadLocal，在虚拟线程下的成本模型和 2009 年不同了。

④ 最大的变化：编译期 AOP 回来了，而且这次是主流

看图上那句话——Micronaut / Quarkus / Dagger 把 DI 和 AOP 一起搬回了编译期。它们在 javac 的注解处理阶段直接生成拦截代码，于是：

运行时代理（Spring AOP / Guice）编译期（Micronaut / Quarkus）
反射大量基本没有
启动秒级毫秒级
原生镜像需要大量 AOT 配置天然支持
自调用问题有没有
final 方法拦不到看实现，限制小得多
代价—构建变慢；调试时看到生成代码；动态性受限

Spring 的应对不是改架构，而是加 AOT：Spring Boot 3+ 的 spring-boot-maven-plugin process-aot 在构建期预生成代理和 bean 定义，为 GraalVM 原生镜像铺路。

⑥ 拦截顺序问题：有了显式控制

书里只能靠"绑定的先后顺序"，这非常脆弱。今天用 @Order / Ordered 显式声明：

@Aspect @Order(1) class HtmlDecoratingAspect { ... }   // 数字小 = 更外层
@Aspect @Order(2) class BoldDecoratingAspect { ... }

Spring 的内置切面之间也有既定顺序（事务、缓存、安全）。但作者的核心告诫依然成立：拦截器的组合语义测不出来，必须写纵向集成测试。今天这类测试就是 @SpringBootTest（第 4 章讲的完整切片）。

⑦ 一条没变的判断

作者说加粗那个例子"其实本来就不该用拦截器，折进模板里更好"。这条依然成立：AOP 适合的是真正的横切关注点（事务、安全、指标、审计、重试），不适合业务逻辑的变体。今天有更多非 AOP 的手段可选——装饰器模式 + @Primary、函数式组合、Micrometer 的 @Observed、Resilience4j 的 @Retry/@CircuitBreaker——这些其实都是"配好的 AOP"，只是你不用自己写拦截器了。

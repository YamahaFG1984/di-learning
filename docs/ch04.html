第 4 章

模块化与可测试性

前三章都在讲"一个对象怎么拿到依赖"。这一章往上抬一层：一堆对象怎么组织成能独立开发、独立替换、独立测试的模块。核心命题只有一个——紧耦合让代码不可测，而不可测的代码等于没写完。

  • 模块的四个性质
  • 横切 / 纵切
  • 紧耦合的重构代价
  • 面向契约编程
  • out-of-container 测试
  • 集成测试
  • 动态重绑定

4.1模块是什么

对象是程序的构件；一组承担共同职责的对象叫模块。作者给了四条判据，今天读起来像是微服务和 Spring Modulith 的预告：

性质含义
完整 Whole一个完整的职责单元，可以整体拔出、整体插入
独立 Independent除了公共库，不依赖其他模块就能完成自己的核心职能，可独立开发和测试
契约可靠 Contractually sound行为有明确定义，在任何情况下都可被信赖
分离 Separate不侵入协作者的内部

关键推论：不同的模块装配方式 = 不同的应用语义。"持久化到数据库"换成"持久化到数据集群"、"Web 界面"换成"桌面 GUI"，只要契约不变，整个应用继续工作。

4.2两个方向的切分

紧耦合的真实代价

}

面向契约编程

契约（接口）远不止是"通信手段"。作者列了五重身份，最后一条是全书的关键：

  • 行为的精确规格说明；
  • 现实业务目的的隐喻；
  • 意图的揭示（该怎么用）；
  • 一种内建的文档形式；
  • 行为验证的基石——验证一个实现是否正确，就是拿它跟契约对照测试。

星巴克点单的契约：

public interface Customer  { void waitInLine(); boolean placeOrder(String choice); void pickup(Coffee c); }
public interface Attendant { boolean takeOrder(String choice); Coffee prepareOrder(); }

注意两个接口都只说做什么，不说怎么做。于是 BrazilianCustomer 可以被 RoboticAttendant 服务，系统行为保持一致。

作者还强调异常也是契约的一部分：如果 takeOrder() 在卖光时应该返回 false，它却返回 true 然后不上单，整个应用就坏了。

最后，契约必须写清楚边界情况——下面这个接口是不合格的：

规格不足
public interface StringSearch {
    boolean contains(String s);
    String startsWith(String fragment);
}
// startsWith 返回哪个匹配？第一个？
// 最后一个？没匹配返回什么？
合格
/**
 * 测试列表中是否有以给定序列开头的字符串。
 * @param fragment 用于搜索的片段
 * @return 返回找到的第一个匹配项，
 *         没有匹配时返回 null。
 */
String startsWith(String fragment);

4.3测试：单元 vs 集成

作者的立场很硬：没有经过形式化验证的代码，价值近乎为零。手工点点菜单不算测试，它漏掉了坏数据、并发瓶颈这些看不见的失效点。

out-of-container 单元测试

public class BookCatalogTest {
    @Test public void freeFormSearch() {
        MockLibrary mock = new MockLibrary();
        new SimpleBookCatalog(mock).search("dependency injection");
        assert mock.foundByKeyword();
    }
}

注意：这里用的是手工构造，没有注入器。依赖只有一两个，全是 mock，为几个 mock 去配一个注入器纯属自找麻烦。

⚠ 反模式："我真的需要我的依赖" 
public class BookCatalogTest {
    private Injector injector;

    @BeforeMethod public void setup() {
        injector = Guice.createInjector(new TestBooksModule());   // 只为测试而存在的配置
    }

    @Test public void freeFormBookSearch() {
        new SimpleBookCatalog(injector.getInstance(Library.class)).search("..");
    }
}

三宗罪：① 测试多了一个对注入器的依赖；② TestBooksModule 是纯粹为测试维护的、不产生价值的代码；③ 注入器配置一旦出错，测试报的是假阴性——你会花几小时在错误的地方找 bug。

作者的判据非常好用："当你发现某个类的依赖没法被 mock 掉，你该重新考虑设计。"

mock 不只是替身，还是行为断言

验证一个类的行为，一半在返回值，另一半在它怎么使唤自己的依赖。这里必须用行为脚本：

@Test public void freeFormBookSearch() {
    Library mock = createStrictMock(Library.class);   // strict = 顺序也要对
    String criteria = "dependency injection";

    expect(mock.findByAuthor(criteria)).andReturn(null);    // 先按作者
    expect(mock.findByKeyword(criteria)).andReturn(null);   // 再按关键字
    Book di = new Book("dependency injection");
    expect(mock.findByTitle(criteria)).andReturn(di);       // 最后按标题

    replay(mock);
    Book result = new SimpleBookCatalog(mock).search(criteria);
    verify(mock);                                // 断言调用方式和顺序
    assert di.equals(result);                    // 断言返回值
}

如果实现改成"优先按标题搜"，这个测试会失败——调用顺序本身就是行为的一部分。

集成测试

集成测试关心的是"拼起来对不对"，所以它可以且应该违反上面那些单元测试规则：

public class HomePageIntegrationTest {
    private Injector injector;

    @BeforeTest public void prepareContainer() {
        injector = Guice.createInjector(new WebModule(),          // 生产模块
                                        new TestPersistenceModule()); // 只有环境差异走替身
    }
    @AfterTest public void cleanup() { ... }

    @Test public void renderHomePage() throws Exception {
        injector.getInstance(HomeServlet.class).service(mockRequest, mockResponse);
    }
}

五条原则：尽量用生产模块；只把环境差异（数据库实例等）抽出来做平行配置；外部交互靠模拟（HTTP 请求）；启动昂贵，所以用 @BeforeTest 只跑一次；必须有 cleanup() 关闭外部资源。

一个很好的判据

"在一个健康的代码库里，集成测试应该很少失败。它揭示的通常是配置怪癖和库的互操作问题，而不是编码错误——那些应该被单元测试覆盖掉。"

如果你的集成测试天天挂在业务逻辑上，说明单元测试覆盖不足。

4.4运行时重绑定

最后一节讲一个高级（且危险）的用法：运行时改变对象图的结构。作者先泼冷水：

⚠ 先读这段警告

"在运行时修改注入器配置和对象模型有潜在危险。没有仔细的库支持，你会失去启动时的校验与安全特性，可能导致不可预测、不稳定、甚至无法检测的 bug。"

五条约束：绑定一旦建立就持续生效直到重绑；已经持有旧实例的对象不会更新；重绑与作用域强相关（长命对象拿着被重绑的键就必须重注入或丢弃）；重绑与生命周期强相关（依赖变更需要通知相关模块）；不是所有注入器都支持。

朴素做法是把两条依赖都注入进去然后用 flag 切换——但这就把基础设施逻辑混进了业务类。Adapter 又一次救场：

public class DependencyAdapter implements Dependency, Rebindable {
    private final DependencyA a;
    private final DependencyB b;
    private boolean useA = true;

    public void rebind()   { useA = false; }
    public int calculate() { return useA ? a.calculate() : b.calculate(); }
}

于是客户端回到干净状态：

public class LongLived {
    private final Dependency dep;     // 只认契约，重绑完全透明
    @Inject public LongLived(Dependency dep) { this.dep = dep; }
    public void go() { int r = dep.calculate(); ... }
}

注意 Rebindable 这个角色接口：控制逻辑只需维护一个 Rebindable 列表，逐个通知即可。这就是第 7 章"多播生命周期"的雏形。

2026 对照

① 集成测试：Testcontainers 改变了一切

原书的集成测试要点是"用一个平行的 TestPersistenceModule 指向测试数据库"。这套做法有个根本缺陷——测试环境和生产环境用的不是同一个数据库（书里的例子用内存 HSQL，生产用 PostgreSQL），于是最该被集成测试抓住的那类问题（SQL 方言、事务隔离级别、索引行为）恰好抓不住。

Testcontainers 把这个缺口补上了：测试时用 Docker 起一个真的 PostgreSQL，用完即弃。

@SpringBootTest
@Testcontainers
class OrderRepositoryTest {
    @Container @ServiceConnection                 // Spring Boot 3.1+ 自动接线数据源
    static PostgreSQLContainer<?> db = new PostgreSQLContainer<>("postgres:17");

    @Autowired OrderRepository repo;

    @Test void 按客户查询订单() { ... }            // 打的是真 PostgreSQL
}

作者那句"集成测试要尽可能贴近生产环境"的原则没变，贴近的程度提高了一个数量级。

② "别在单元测试里启动容器"：官方立场一致

Spring 为此提供了测试切片——不是全有或全无，而是按层加载：

粒度写法加载什么
纯单元new Service(mock(Dao.class))什么都不加载 —— 首选
Web 层切片@WebMvcTest(OrderController.class)只加载 MVC 相关 bean，服务层用 @MockitoBean
持久层切片@DataJpaTest只加载 JPA 相关 bean
完整集成@SpringBootTest整个应用上下文 —— 用最少

这正是原书的分层测试观点被产品化的结果。补充：@MockBean 在 Spring Boot 3.4 起被 @MockitoBean 取代。

③ 工具链换代

书中今天
TestNG / JUnit 4JUnit 5（@BeforeEach/@BeforeAll、参数化、嵌套测试）
EasyMock（createStrictMock/replay/verify）Mockito（mock()/when()/verify()）；顺序断言用 InOrder
assert x : "msg"（需要 -ea）AssertJ assertThat(x).isEqualTo(y)
 
// 上面那段 EasyMock 脚本的 Mockito 版本
@Test void 按作者关键字标题的顺序搜索() {
    Library lib = mock(Library.class);
    Book di = new Book("dependency injection");
    when(lib.findByTitle("dependency injection")).thenReturn(di);

    Book result = new SimpleBookCatalog(lib).search("dependency injection");

    InOrder order = inOrder(lib);                       // 顺序断言
    order.verify(lib).findByAuthor("dependency injection");
    order.verify(lib).findByKeyword("dependency injection");
    order.verify(lib).findByTitle("dependency injection");
    assertThat(result).isEqualTo(di);
}

④ "不同部署剖面"：已经标准化了

4.4 节那套手写 Rebindable 的方案，今天只在"不重启就要切换"这个极窄的场景才需要。绝大多数"不同环境用不同实现"的需求，由配置机制直接解决：

@Profile("local")      @Bean Library fileLibrary()     { return new FileLibrary(); }
@Profile("production") @Bean Library databaseLibrary() { return new DatabaseLibrary(); }

@ConditionalOnProperty(name = "search.engine", havingValue = "elastic")
@Bean SearchEngine elastic() { ... }

真正需要运行时切换的场景（灰度、开关），今天交给专门的 feature flag 系统（Unleash、LaunchDarkly、或自研配置中心 + @RefreshScope），而不是去动注入器的绑定表。作者的警告依然有效，只是我们把这类需求外包出去了。

⑤ "模块"从概念变成了可执行约束

2009 年，模块的四条性质只能靠自觉。今天有工具强制执行：

  • JPMS（Java 9+ module-info.java）：在语言层面声明"我导出哪些包、依赖哪些模块"。
  • ArchUnit：把架构规则写成测试——noClasses().that().resideInAPackage("..domain..").should().dependOnClassesThat().resideInAPackage("..infra..")。
  • Spring Modulith：单体应用内的模块边界校验 + 模块级集成测试 + 自动生成模块文档。它几乎是把本章的四条性质做成了库。
  • 包级私有（第 9 章会详述）：最低成本、零依赖的模块边界手段，至今仍然最有效。

⑥ 契约的表达变强了

// sealed 接口：契约现在可以「封闭」实现集合，编译器能做穷尽性检查
public sealed interface SearchResult permits Found, NotFound {}
public record Found(Book book) implements SearchResult {}
public record NotFound() implements SearchResult {}

// 于是 4.2 节那个「没匹配时返回 null」的规格问题，从注释变成了类型
SearchResult r = search(criteria);
String msg = switch (r) {                       // 漏掉分支 = 编译错误
    case Found f    -> f.book().title();
    case NotFound n -> "未找到";
};

作者当年只能靠 Javadoc 约定"没匹配返回 null"。今天 sealed + record + 模式匹配（Java 21 正式）能把这条规格写进类型系统，编译器替你验证。Optional<T> 是更轻量的同类手段。
